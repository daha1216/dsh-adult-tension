# 加内容

> 职责导航与素材分层见 `references/素材架构.md`；本文件规定 L0-L3 编辑、构建、审查同步与验证流程。新增文件同步 `maintenance/data_manifest.yaml`，不要复制数据清单到另一套运行配置。

本文件是素材维护手册。核心池在 `scripts/data/` 编辑；框架在 `authoring/frameworks/<ID>.yaml` 编辑，`scripts/data/world_frameworks.yaml` 是生成文件。生产开局不读取本文件，主要运行宿主为 DeepSeek Harness。

## 1. 先判断改动等级

素材变更会使旧来源哈希对应的审查失效。`sync_governance.py --write` 汇入当前人工决定与精确清理记录，校验后紧凑写入 registry；它不自动授予语义通过。`NOT_REVIEWED` 不得被写成“已闭合”。运行时 auto 只读取构建聚合中的有效审查集，没有合格框架时报错，无隐式 legacy 回退。

不要先改文件，再靠报错猜影响范围。先按下面四级判断：

| 等级 | 典型内容 | 处理方式 |
|---|---|---|
| L0 单文件文案 | 不改键、ID、占位符或含义的表达修正 | 只改原编辑源，更新受影响审读；运行 `qa.py --changed` 或定向检查，不借文案修改放宽约束 |
| L1 单表素材 | 一个压力来源、社会规则、张力引擎、玩家称谓 | 检查 meta 名单、引用与模板映射，登记适用边界；通过 `--material` 或 `--changed` 检查 |
| L2 跨表素材 | 地点、身份族、处境、动作，或单框架配套 | 同步第 3 节关联文件及依赖清单，构建聚合、同步审查，再用 `--framework` 或 `--changed` 验证两模式配套 |
| L3 结构能力 | 抽取轴、状态字段、枚举、事件类别、运行规则 | 按功能开发处理，同步脚本、schema、文档与测试；执行 `qa.py --full`，发布另加 `--release` |

新增一个地点、身份族、处境或动作，默认按 L2 处理，不要把它当成单文件增删。

## 2. 标准维护流程

日常顺序固定为 **编辑 authoring → build_frameworks --write → sync_governance --write → qa**。核心池仍改原数据文件；新增数据文件时先维护职责清单。按需更新人工 review 后再执行：

```text
python scripts/build_frameworks.py --write
python scripts/sync_governance.py --write
python scripts/qa.py --changed
```

`build_frameworks` 按 `authoring/framework_index.yaml` 顺序生成聚合，只有来源哈希匹配且语义检查有效的 review 才进入 reviewed_frameworks。不带 `--write` 时只检查聚合是否新鲜。`sync_governance` 不带 `--write` 只预览审计；写入模式汇入 `maintenance/framework_reviews/*.yaml`、`maintenance/core_review_decisions.yaml` 和脚本限定的精确清理记录，保留 registry 的旧来源与 history。

| QA 入口 | 范围 |
|---|---|
| `qa.py --changed` | 相对 merge base 的改动及依赖；单框架源或 review 连同生成聚合、registry、指纹的改动保持框架级抽样，聚合一致性仍先检查；其他共享改动可扩大范围，可用 `--base` 指定基线 |
| `qa.py --framework <名称>` | 定向框架结构、配套和抽样回归 |
| `qa.py --material <稳定ID>` | 框架 ID 选择对应框架范围；其他素材 ID 根据维护登记定位文件并展开依赖检查 |
| `qa.py --full` | 全量结构、内容体检与回归，不代表语义和实玩已通过 |
| `qa.py --full --release` | 全量检查后另核验当前人工审查、清理及真实模型证据 |
| `qa.py --full --update-fingerprint` | 完整检查通过且数据未再变化后更新 `maintenance/content_fingerprint.txt`；不是跳过失败的开关 |
| `qa.py --changed --plan` | 只显示范围与命令，不执行检查或写入 |

`--release`、`--update-fingerprint` 都必须与 `--full` 配合。共享工作树协作期间只运行自己负责的定向测试，避免其他人的中间态造成误判；由主工作流在收口时执行全量 QA。记录实际命令、结果、未完成项和 seed 漂移，不手改测试中的 EXPECTED 伪造指纹通过。

素材池变化后，同一个 seed 抽出不同开局是预期行为；旧存档不因素材变化而自动重写。固定 seed 只保证同一版本素材和脚本下的确定性，不保证跨版本结果不变。

维护诊断仍可单独运行，但不能代替统一流程：

```powershell
python -X utf8 scripts/material_registry.py --summary
python -X utf8 scripts/material_quality.py --summary
python -X utf8 scripts/check_duplicates.py
python -X utf8 scripts/analyze_content.py --samples 1000
python -X utf8 scripts/playtest_report.py
```

`analyze_content.py` 默认使用 `--framework auto --opening-mode pressure`；全量 QA 的分布分析同样采用默认 auto 的 1000 次抽样。核对独立旧池时运行 `python -X utf8 scripts/analyze_content.py --framework legacy --samples 1000`；日常分布另加 `--opening-mode daily`。报告须标明框架范围与开局模式，不能把 legacy 分布当作默认玩法证据。

`check_duplicates.py` 对照 `maintenance/duplicate_reviews.yaml` 检查重复候选，不自动删除或合并。当前 1 组近重复因吸引对象不同保留，4 组跨表同句因分类索引引用保留；句式相近或显示名称相同不等于冗余。当前 26 项人物资源复用候选来自前 13 个框架中同两种职业互换玩家/NPC 视角，不能宣传为 26 套全新人物；角色差异仍须逐项审读。

`references/material_registry.yaml` 只供维护工具读取；紧凑写入不能丢失有效人工决定或 history。两个已证实不可达的处境模板与用户明确排除的框架按第 14 节直接清理并登记证据，不为消除 warning 回填运行池。

## 3. 常规扩充对照表

| 我想加/改…… | 改哪个文件 | 必须同步或检查 |
|---|---|---|
| 一个世界框架 | `authoring/frameworks/<ID>.yaml` | 必须同时填写兼容时代、美学、地点画像、人物搭配、日常活动、地方细节和压力情境；执行 build_frameworks --write 生成聚合，再同步审查并跑两种模式抽样，不得只新增名称 |
| 一个地点 | `pools.yaml`「时代与地点·地点」 | `locations.yaml` 加房间细节；`location_profiles.yaml` 补隐私、可见度、出口、见证者、可用行动、压力修饰；时代专属地点再同步 `meta.location_eras` |
| 一个时代 | `pools.yaml`「时代与地点·时代」 | `names.yaml` 的 `eras` 键名逐字一致；可补姓氏、男性名、女性名专属池，不补则回落通用池 |
| 一类身份圈层 | `pools.yaml`「身份侧」 | `identities.yaml` 的 `npc` 下至少加入一个具体身份；需要调整抽取倾向时同步 `meta.identity_weights` |
| 一个具体身份 | `identities.yaml` | 检查资源、限制、暴露风险和公开身份是否具体；必要时补 `identity_profiles.yaml` |
| 一种处境 | `pools.yaml`「处境侧」 | 压力模式在 `templates.yaml` 配齐 `situation_beats` 五键；若用于日常开局，还须在 `pools.yaml` 的 `meta.daily_opening.处境` 中引用原条目并配齐同名五键的低压解释 |
| 一个张力引擎 | `pools.yaml`「张力引擎」 | 压力模式默认需要两项；若要用于日常开局，必须确认该方向可自然低压呈现，并加入 `meta.daily_opening.张力引擎`，否则仅压力模式可用；若属于把柄或杠杆型引擎，同步 `meta.leverage_engines` |
| 一个压力来源 | `pools.yaml`「压力来源」 | 压力模式使用；日常模式不接受外部压力来源。若带死线，同步 `meta.timed_pressures`；确认它描述的是外部由头，不是人物当前处境 |
| 社会规则、核心规则、美学基调 | `pools.yaml` 对应表 | 写实美学基调同步 `meta.gate_aesthetics`；检查是否能转成具体世界常量 |
| 一个开场动作 | `pools.yaml`「场景动作」对应桶 | 非交易动作必须在 `action_categories.yaml` 分类，并在 `action_metadata.yaml` 配功能、可见度、升级度；建议同步 `templates.yaml` 的专属句式和玩家优先建议 |
| 一种性格反差 | `pools.yaml`「反差轴」 | 建议在 `templates.yaml` 的 `contrast_line` 配专属表现；不得改变亲密画像或许可规则 |
| 一个决策轴条目 | `character_meta.yaml`「决策轴」 | 压力策略应配撤回信号和压力反应；检查是否会让角色失去自主判断 |
| 一个玩家称谓 | `pools.yaml`「玩家化身轴·称谓」 | 检查称谓不会暗示未成年或固定职业 |
| 一个玩家年龄段 | `pools.yaml`「玩家化身轴·年龄段」 | `character_meta.yaml`「年龄段区间」配置合法 `[最小, 最大]` |
| 一个玩家社会位置 | `pools.yaml`「玩家化身轴·社会位置」 | `identities.yaml` 的 `player` 加身份；`character_meta.yaml` 配关系起点 |
| 表层风味、口癖、外观 | `character_pools.yaml` 对应组 | 单项不超过 8 字；外观保留写实门控依赖的键名 |
| 一个中期转折方向 | `twists.yaml` 对应类 | 七类不可增删改名；类内条目必须有具体影响，不只写抽象意外 |
| 一个地点行为画像 | `location_profiles.yaml` | 覆盖所有地点族；补隐私、可见度、出口、见证者、可用行动、压力修饰 |
| 一类非交易动作 | `action_categories.yaml` | 动作必须存在于 `pools.yaml`；每个动作只能归入一个分类 |
| 一类动作元数据 | `action_metadata.yaml` | 覆盖动作分类，并填写 `function`、`visibility`、`escalation` |
| 一族身份行为画像 | `identity_profiles.yaml` | 覆盖身份族；填写谈判、冲突、修复、公开/私下转换、跟进、退出和证据习惯 |
| 一类转折画像 | `twist_profiles.yaml` | 七类全部覆盖；填写影响范围、升级度、退出机会和第三方介入 |
| 开局文案 | `templates.yaml` | 检查占位符、语义层级和是否能适配不同 NPC；`{npc}` 会替换为主 NPC 姓名 |
| 起名用字 | `names.yaml` | 允许跨时代、跨性别池重复；运行时再通过近期历史和本局已用名降低撞名 |

日常开局不是把压力词改名。它只复用已存在的核心规则、社会规则、处境、场景动作和可选张力引擎，并通过 `meta.daily_opening` 登记允许项及处境低压解释；这些筛选轴新增条目未经登记时默认只可用于压力模式。

三张压力表必须保持语义分层：**张力引擎**是整晚的动态戏路，**压力来源**是外部现实由头，**处境侧**是人物正在承受的具体问题。三者不得逐字重名；近义词也必须能在事件中承担不同功能。详见 `references/开局流程.md` 第 4 节。

### 3.1 日常模式登记

在原素材表维护名称，日常登记只引用名称，不复制整套素材池。日常开局的核心规则、社会规则、处境、动作与可选引擎必须出现在 `pools.yaml -> meta.daily_opening` 对应字段；世界、身份、外观与称谓继续使用原有兼容规则。新增的这些日常筛选轴未经登记不会进入日常开局，其他共享轴仍按原规范维护。

核心规则、社会规则、张力引擎、场景动作填写名称列表；场景动作须属于“非交易靠近”，并保留动作分类与元数据。处境填写名称到五键文案的映射。以下展示字段格式，示例名称必须先在原处境池存在：

```yaml
meta:
  daily_opening:
    处境:
      今夜话没说完:
        trigger: "{npc}把杯子放下，接着刚才的话题。"
        objective: "分享一件近况。"
        choice: "继续聊，还是改天再说。"
        immediate: "话题暂时停在两人之间。"
        near: "下次见面仍可接着聊。"
```

把字段合并到现有 `meta.daily_opening`，不要重复声明 YAML 键或覆盖已有登记。文案仅支持 `{npc}` 和 `{pressure}` 占位符（日常的 pressure 为空）；`immediate/near` 是现状与可选后续的叙述，不会据此创建事件。不要把催债、审查、断供或伤病倒计时改个名字冒充日常。是否低压须由维护者审读，体检只能检查登记引用、类型、重复值、五键完整性与占位符。

登记后同步治理并执行相关 QA；需要核对旧池时显式指定 `--framework legacy`，不要靠 auto 回退。结构检查使用 `sample_materials.py` 的内存抽样，不写工作档、不追加历史；普通 build_opening --complete 即使指定 --out/--no-working，成功仍会追加历史，不能把它当无副作用抽样。

## 4. 新题材与新场景模板

新增题材不要只加一个名词。至少填写下面这份维护草案，再决定落在哪些数据表：

```text
题材名称：
核心矛盾：谁与谁因为什么资源、信息或规则发生拉扯
世界初印象：玩家第一眼能感知的制度、氛围或异常
适配时代/地点：
适配身份族：
人物正在承受的处境：
外部压力来源：
可用非交易动作：至少 3 个，分别提供靠近、确认、退出或转移功能
可见度与见证者：谁能看见，谁可能介入
退出通道：离开、暂停、转交、公开化或延后处理的方式
immediate：本拍已经存在的压力
near：下一阶段可能兑现的事件
far：只留下钩子的长期变化
可用转折类别：
容易和现有素材重复的词：
```

新场景至少应同时具备一个空间特征、一个社会规则、一个可用资源、一个限制条件和一个退出通道。只有氛围，没有行动与选择的场景，不建议加入地点池。

## 5. 素材质量验收

新增条目必须附带登记信息：稳定来源路径、架构层、模式、时代/地点/主题、配套框架或 `shared/legacy`、退出点、持久后果、重复检查结果和抽样 seed。没有这些信息的条目不得进入发布候选。起名按时代和生活背景判断，不局限现代姓名；仅新局按世界观、人物、正文三个标题输出，前两项各 1-2 句，载入与续玩不重复。

每条新增素材至少通过以下检查：

- **可演出**：能转成具体人物、物件、动作或现场反应，而不是只表达情绪标签。
- **可选择**：给玩家留下至少一种确认、靠近、转移、暂停或退出的接手点。
- **可区分**：与同表条目功能不同，与三层压力表不逐字重名。
- **可反应**：NPC 能根据目标、知识、资源和身份做出不止一种合理反应。
- **可回收**：能形成事件、关系、资源、信息或后续压力中的至少一种持久影响。
- **不越权**：不替玩家决定关键选择，不把处境词直接写成服从、许可或已发生行为。
- **能落地**：地点有空间细节，身份有资源和限制，动作有可见度和升级度，转折有影响范围和退出机会。

文案验收再检查三点：是否自然、是否能被不同名字和身份替换、是否避免连续使用同一种句式。模板可以保留通用兜底，但高频或关键动作应优先补专属表达。

## 6. WARNING 分级与处置

`WARNING` 不是“全部忽略”，也不是“全部阻断”。按影响分级：

| 等级 | 例子 | 处置 |
|---|---|---|
| P1 | 关键动作无分类、重要地点画像缺失、文案会改变玩家对事件的理解 | 本轮必须处理或暂不上线 |
| P2 | 高频动作缺少专属句式或玩家优先建议、身份画像缺少个性化行为 | 建议本轮处理；确认兜底仍自然后可暂留 |
| P3 | 低频条目使用通用句、权重未单独配置、非关键反差没有专属台词 | 可保留，记录为待治理项 |

当前体检的判断口径是：`ERROR` 必须修复；`WARNING` 需说明等级、影响和是否接受兜底。最终以“无 ERROR、P1 已处理、P2/P3 有记录”为完成标准，不要求 WARNING 数量为零。

## 7. 需要改代码的扩充

以下才属于 L3 结构改动：

1. **新增整条抽取轴**：同步 `roll_opening.py` 的抽取计划、模式/锁定解析和 `fill_opening.py` 的填装逻辑。
2. **新增状态字段或枚举**：同步 `validate_state.py`、`references/状态总结.md`、相关 live slice 和测试。
3. **新增事件类别或运行规则**：同步 `commit_turn.py`、`references/世界运转.md`、命令契约和回归测试。

换场场景身份本身不属于必须改代码的扩充。新增空间词通常只需要完善地点、地点画像和场景语义；只有引入新的状态字段或运行分支时才升级为 L3。

## 8. 变更记录与回滚

每次素材治理至少记录：

```text
日期：
目标题材/问题：
改动等级：L0/L1/L2/L3
新增、删除或改名：
影响文件：
check_content：ERROR/WARNING 数量与 P1/P2/P3 处置
抽样 seed：
固定 seed 是否漂移：
内容指纹：旧值 -> 新值
回滚方式：恢复哪些 YAML、脚本或测试基线
```

删除或改名键名、ID、枚举或模板占位符前，搜索代码、测试、文档和数据引用；普通文案值优先搜索数据、体检与指纹相关引用。已经写入旧存档的事件 ID、关系 ID 和历史摘要不得因素材治理而重建；素材回滚只影响之后的新开局。

## 10. 兼容元数据填写规范

新增会受上下文影响的素材时，除池条目外同步填写 `meta.material_compatibility`：

```yaml
素材名: {eras: [适用时代], places: [适用地点], themes: [主题标签]}
```

身份族、玩家社会位置、压力来源和场景动作至少填写 `eras` 或 `places`；外观条目应注明适用的世界类型、美学族或解释方式。玩家称谓应与社会位置的语体和权力关系相容。张力引擎、压力来源、处境至少共享一个主题标签；无法共享时应改写或明确桥接。开局结果中的 `兼容性` 是最终检查记录，`pass` 可直接使用，`bridge_required` 必须交代来源。

## 11. 一句话自查

发布级改动或 L3 结构改动后执行：

```text
python scripts/build_frameworks.py --write
python scripts/sync_governance.py --write
python scripts/qa.py --full
# 发布核验证据；需要更新指纹时显式附 --update-fingerprint
python scripts/qa.py --full --release
```

结构通过不等于语义通过，不等于 320 条实玩响应已完成。先确认无 ERROR、P1 已处理，再核对与当前来源一致的审查和实玩证据；不把单测数、内存开局数或分数阈值写成已完成数字。

## 12. 维护登记决定格式

登记文件不是素材池、抽取白名单或存档。来源字段盘点和维护单元的粒度不同：一个框架、一组姓名或一个画像字段可以是一条维护单元；字段数量不能代表逐条文案审查数量。

稳定 ID 由来源文件、父路径、条目名称和同名出现序号生成；新增不同名称的列表项不改变原有 ID。改名或移动来源会形成新 ID，原 ID 留作历史，必须按弃用流程处理，不自动改写旧存档。

同步不会代读内容。提交审查决定前必须读对应内容及实际消费者，不能只看名称或哈希。核心池决定放在 `maintenance/core_review_decisions.yaml` 的 YAML 列表中；框架专用 review 放在 `maintenance/framework_reviews/<ID>.yaml`，不得把两种格式混用。下面是核心池决定格式，值必须来自当前登记：

~~~yaml
- id: 从登记表复制稳定ID
  source_hash: 从登记表复制当前哈希
  status: KEEP_SHARED
  modes: [daily, pressure]
  owners: [shared]
  compatibility:
    eras: []
    places: []
    themes: [填写实际主题]
    technology_boundary: 写明依赖的器物、制度和不适用场景
    bridge_status: not_required
  restrictions:
    frozen: false
    restricted: false
    reason: 写明本次审查的限制范围
  review:
    scope: 精确说明读过哪些条目和消费者
    reason: 说明地点、人物、选择后果和模式如何配套
    release: governance-1
~~~

空时代或地点列表只表示没有登记枚举，不代表全时代或全地点放行。跨时代器物、异文化移植、特殊制度的桥接未解决时用 `BRIDGE_REQUIRED`，并在技术边界中写清所需解释，不直接扩大运行时白名单。

| 状态 | 使用条件 |
|---|---|
| KEEP_FRAMEWORK | 已读过具体框架的实际配套，owners 写真实框架名 |
| KEEP_SHARED | 可在明确条件下共享，记录条件和原有运行入口 |
| KEEP_LEGACY | 保留原有独立抽取入口，不声称已纳入闭合框架 |
| BRIDGE_REQUIRED | 已识别真实冲突或缺少连接条件，不能自动放行 |
| DUPLICATE | 已判断为同一功能重复，canonical_id 指向仍存在的条目 |
| DEPRECATED | 无效候选已经确认，保留来源和弃用原因 |
| FROZEN_RESTRICTED | 只登记来源、范围与限制，不扩写、重构或放宽 |
| NOT_REVIEWED | 尚未完成所声明单元的语义审查 |

活动功能标记放在维护层 `activity_functions`，可用调查、创作、照护、修复、观察、移动、社交、交易、退出等。标签必须反映实际动作，不能只改标签就宣称新增玩法；不替换运行时的 category/function 枚举。

框架 review 须匹配当前 `id/name/source_hash`，明确 `semantic_status: REVIEWED` 与具体 reason。checks 至少覆盖 `era_and_theme`、`space`、`people`、`daily`、`pressure_bindings`、`distinct_functions`，逐项基于实际审读填写，不能靠批量置 true 放行。来源变化后旧 review 无效。

框架审查使用 `quality: {grade: B, reason: ...}`；A/B/C 分别表示明显独特、结构闭合但仍有复用、玩法差异不足，存在未解决冲突时用 REVIEW_REQUIRED。脚本给出的 structural_grade 只作初筛，不覆盖审读分级。

关系化学放在维护层 `chemistry.pairs`，按人物搭配索引记录 `needs`（双方需求）、`misreading`（可能的误读）、`asymmetric_cost`（不对称代价）、`ritual`（共同仪式）、`conflict_loop`（冲突循环）、`repair`（修复动作）、`irreversible_threshold`（不可逆阈值）。这是作者配套说明，不是自动写入角色历史的事件。

## 13. 新框架交付清单

每套新增框架须同时具有时代、技术边界、美学、核心与社会规则、地方习俗及主题；3至8个不同功能地点、至少2组人物、3种真实不同功能的日常活动、2个压力情境。地点须有独特空间用途、见证者和可用出口；双方的身份、资源、权限、限制、称谓和相识理由不能只替换名词。

日常活动须有相遇理由、可接手动作、退出点和自然后续，不自动调用外部压力来源、近端或远期事件。压力情境须有来源、双引擎、即时及近端后果、远期钩子和退出方式；逐一检查活动所允许的角色能否理解并参与压力处理，不能假设笛卡尔积中的所有组合都合理。

框架自带的作品、种子、排期制度、地方习俗等至少有一项改变玩家的实际选择。仅新增一个世界名、换掉活动名词或把信息交换重新贴标签，不算覆盖新题材。

## 14. 有证据的直接清理

可证实不用或被用户精确排除的对象，可以直接清理，不强制保留一个版本周期。先记录精确来源文件、路径、稳定 ID、原 source_hash、消费者与引用搜索、删除原因和实际回归证据，再按 `cleanup.policy: verified_direct`、`cleanup.stage: removed`、`cleanup.regression_evidence` 登记；保留旧记录及 history。重复项还须指出 canonical_id，近重复但语境不同的内容不能自动合并。

`sync_governance.py --write` 只汇入脚本限定的精确清理对象与人工决定，不是通用批量删除器。证据不足时保持候选，不为清警告改写运行资格。不删除共享池依赖、旧存档快照或冻结对象；新类型清理若需要脚本支持，转 L3 给负责脚本的维护者。

~~~powershell
python -X utf8 scripts/sync_governance.py --write
python -X utf8 scripts/qa.py --full --release
~~~

已删除的 `references/governance_decisions.yaml` 含 10 份历史 review，其来源已失效或对应框架被用户排除，不再作为当前审查输入；原文可由 git 与登记 history 追溯。当前人工框架结论只放 `maintenance/framework_reviews/*.yaml`，不要恢复旧文件来填满通过数。

## 15. 实玩与发布证据

实玩主宿主是 DeepSeek Harness。基线在 `maintenance/baseline.yaml`：40 框架、daily/pressure 两模式、seed 11，每组新局加 3 次续写，要求至少 320 条真实模型响应。这是验收要求，不是已完成声明。

`run_playtest.py` 必须显式调用，会消耗模型额度；默认 QA 不会自动调用它。需要实际生成时，明确选择框架后执行 `python scripts/run_playtest.py --framework <名称>`，可重复该参数；Windows 可用 `--dsh-entry <bin.js>` 指定 DSH 入口。脚本按当前来源哈希记录输出到 `maintenance/playtests/`，已有证据过期时不得伪装成新结果。

续跑和证据核验都重建当前运行摘要、提示词及已记录历史，并检查每回合 `prompt_sha256`。输入已变化时，先原样归档旧回复和评分，再补跑受影响案例；不能只改协议名、更新时间或覆盖失败。已有结果低分但输入未变，不属于过期证据。

`python scripts/playtest_report.py` 只检查已有 320 条证据与独立评分，不调用模型。每组应有来源、模式、seed、宿主版本、原始请求与响应、时间戳；独立 reviewer 不能等于 generator，评分须绑定 transcript_sha256 并引用原文。每回合单独评五维：世界辨识度、人物可信度、选择意义、后果连续性、表达自然度；记分范围 0-2，达标要求每维至少 1、总分至少 8、阻断项为空，证据须出自该回合。案例汇总使用最低总分回合的完整分数组合，不能用其他回合补分。缺响应、未评分、哈希过期或证据不足都不是完成。

`qa.py --full --release` 核验这些证据与语义审查，不会补跑模型。核心条目仍有 `NOT_REVIEWED` 或 `BRIDGE_REQUIRED`、实玩不完整或未达标时，发布门禁明确失败；桥接可以作为维护中的合法处置，不能冒充精品化收尾。当前 headless 探针使用运行摘要和对话重放，不替代完整 Skill 的逐回合状态提交与 Web 端到端验收。SKILL 冻结整节必须逐字节匹配 `maintenance/baseline.yaml` 的 SHA256；L0-L3 都不授权修改它。
