# 响应时间优化

## 概述

响应时间优化旨在改善用户感知体验，特别是在长时间操作（如完整开局、深度校准）期间。总耗时不变，但通过流式反馈和并行化减少用户等待的焦虑感。

> **执行口径**：本节是设计参考。按 `SKILL.md`「完整开局」，开局必须一次回复完成、不输出中间态；若运行环境支持流式输出，可按下方第 1 节的进度提示作为可选实现，不改变最终输出格式。

## 优化策略

### 1. 开局流式反馈

#### 问题
完整开局需要执行 14 个步骤，涉及多次脚本调用和内容生成，可能耗时 30-60 秒。用户在此期间看到空白，不知道系统是否在工作。

#### 解决方案
在关键节点输出简短进度提示，然后立即继续后台处理。提示不等待用户输入，只是告知当前阶段。

#### 实现方式

```python
# 伪代码示例
def execute_opening():
    # 阶段 1：结构骰和世界框架（步骤 1-5）
    output_progress("⚙️ 正在构建世界框架...")
    roll_result = run_roll_opening_script()
    build_tension_engine(roll_result)
    build_power_dynamics(roll_result)
    build_identities(roll_result)
    
    # 阶段 2：人物和关系（步骤 6-10）
    output_progress("⚙️ 正在塑造人物关系...")
    generate_npc_characters(roll_result)
    build_relationships()
    generate_intimacy_profiles()
    
    # 阶段 3：故事开场（步骤 11-14）
    output_progress("⚙️ 正在编织故事开场...")
    generate_pressure_seeds()
    generate_opening_hooks()
    generate_current_node()
    validate_opening()
    
    # 最终输出完整开场
    output_complete_opening()
```

#### 进度提示格式

```
⚙️ 正在构建世界框架...
[继续执行，不等待]

⚙️ 正在塑造人物关系...
[继续执行，不等待]

⚙️ 正在编织故事开场...
[继续执行，不等待]

【世界观背景】
...
```

#### 注意事项

- 提示必须简短（不超过一行）
- 提示后不等待用户输入
- 不暴露后台步骤号或字段名
- 不展示骰子结果或中间产物
- 最终一次性输出完整开场

### 2. 脚本调用并行化

#### 问题
开局流程中多次串行调用脚本：
1. `roll_opening.py` - 生成结构骰
2. `build_opening.py` - 生成骨架
3. `validate_state.py --profile opening` - 校验

串行执行总耗时 = 各脚本耗时之和。

#### 解决方案
将独立的脚本调用并行执行，利用多核 CPU 减少总耗时。

#### 实现方式

```python
import concurrent.futures
import subprocess

def execute_opening_parallel():
    # 第一阶段：roll_opening.py 必须先执行
    roll_result = subprocess.run(
        ["python", "scripts/roll_opening.py", "--seed", seed],
        capture_output=True,
        text=True
    )
    roll_data = json.loads(roll_result.stdout)
    
    # 第二阶段：build 和 validate 可以准备（但 build 需要 roll 结果）
    # 先执行 build
    build_result = subprocess.run(
        ["python", "scripts/build_opening.py"],
        input=json.dumps(roll_data),
        capture_output=True,
        text=True
    )
    state_data = json.loads(build_result.stdout)
    
    # validate 可以在 build 完成后立即执行
    # 同时其他内容生成也可以并行
    with concurrent.futures.ThreadPoolExecutor(max_workers=3) as executor:
        # 并行执行：校验、玩家化身生成、开场叙事
        future_validate = executor.submit(
            validate_opening, state_data
        )
        future_player = executor.submit(
            generate_player_avatar, state_data
        )
        future_narrative = executor.submit(
            generate_opening_narrative, state_data
        )
        
        # 等待全部完成
        validate_result = future_validate.result()
        player_data = future_player.result()
        narrative = future_narrative.result()
    
    return combine_opening_results(
        state_data, player_data, narrative
    )
```

#### 可并行的任务

- ✓ 校验与内容生成
- ✓ 玩家化身生成与 NPC 细节填充
- ✓ 开场叙事与压力种子展开
- ✗ 结构骰必须在最前（其他依赖它）
- ✗ 骨架生成必须在结构骰之后

#### 预期效果

假设：
- `roll_opening.py`: 5 秒
- `build_opening.py`: 10 秒
- `validate_state.py`: 3 秒
- 内容生成（玩家化身、叙事）: 8 秒

**串行总耗时**: 5 + 10 + 3 + 8 = 26 秒

**并行总耗时**: 5 + 10 + max(3, 8) = 23 秒

实际优化幅度取决于各步骤耗时分布，但可减少 10-20% 总耗时。

### 3. 深度校准的预警

#### 问题
每 5 回合触发一次深度校准，可能导致该回合响应变慢。用户不知道为什么某些回合比其他回合慢。

#### 解决方案
在即将触发深度校准的回合末尾添加不可见标记，让用户对下一回合可能稍慢有心理预期。

#### 实现方式

```python
def render_turn_output(turn_number, narrative, full_calibration_due):
    output = narrative + f"\n\n回合：{turn_number}\n"
    
    # 检查下一回合是否会触发深度校准
    if (turn_number + 1) % 5 == 0 or full_calibration_due:
        # 添加不可见提示（可选）
        # 或者在正文末尾用自然语言暗示
        pass  # 实际不输出，只是内部知道
    
    return output
```

实际上，这个优化的效果主要是让系统知道下一回合会慢一些，但不一定显式告知用户。用户通过体验会发现某些回合稍慢，这是正常现象。

#### 触发条件（复习）

立即触发 `force_full` 的情况：
- 场景或地点改变
- 参与者增减
- 边界变化
- 同意状态变化
- 指令适配改写世界常量/身份/能力/关系
- 快进或跨天
- 载入存档

这些情况用户通常能理解为"重大变化"，对稍慢的响应有容忍度。

### 4. 增量存档

#### 问题
每次"存档"都生成完整 v3 YAML，包含所有历史、状态和检查点。随着游戏进行，存档越来越大，生成和读取都变慢。

#### 解决方案
自动在后台维护增量存档点，只在用户明确要求时输出完整 YAML。

#### 实现方式

```python
# 自动增量存档（后台）
def auto_save_checkpoint(state, turn_number):
    if turn_number % 3 == 0:  # 每 3 回合
        checkpoint = {
            'turn': turn_number,
            'timestamp': get_utc_timestamp(),
            'scene_id': state['current_node']['scene_id'],
            'location': state['current_node']['location'],
            'participants': state['current_node']['participants'],
            'relationships': state['relationships'],
            'events': state['events'],
            'instructions': state['instructions'],
            'checkpoint': state['checkpoint']
        }
        save_to_incremental_slot(checkpoint)
        
        # 只保留最近 10 个增量点
        cleanup_old_checkpoints(keep=10)

# 用户明确要求"存档"时
def export_full_save(state):
    # 输出完整 v3 YAML
    return generate_v3_yaml(state)

# 快速保存（qs）时
def quick_save(state):
    # 使用当前最新的增量点
    # 只更新差异部分
    latest_checkpoint = get_latest_checkpoint()
    delta = compute_delta(latest_checkpoint, state)
    save_delta(delta)
```

#### 用户体验

- 用户输入"存档/s"：生成完整 YAML（可能较慢，但明确要求）
- 用户输入"qs"：快速保存到当前槽（使用增量，很快）
- 系统自动提示"快速保存"：距上次 > 5 回合时

#### 恢复机制

```python
def restore_from_incremental(checkpoint_id):
    # 从最近的完整检查点开始
    base_state = load_base_checkpoint()
    
    # 应用所有增量
    deltas = load_deltas_after(base_state['turn'])
    for delta in deltas:
        base_state = apply_delta(base_state, delta)
    
    return base_state
```

### 5. 懒加载 references

#### 问题
SKILL.md 要求按需加载 references：
- 新开局 → 读 `开局流程.md`、`角色设计.md`
- 快进 → 读 `世界运转.md`
- 存档 → 读 `状态总结.md`

但实际执行时可能提前加载所有文件，浪费时间。

#### 解决方案
严格按需加载，只在真正需要时读取对应文件。

#### 实现方式

```python
# 不要在初始化时加载所有 references
class NarrativeEngine:
    def __init__(self, skill_base_dir):
        self.skill_base_dir = skill_base_dir
        self.loaded_refs = {}  # 缓存已加载的
    
    def load_reference(self, ref_name):
        if ref_name not in self.loaded_refs:
            path = os.path.join(
                self.skill_base_dir, 
                "references", 
                ref_name
            )
            with open(path, 'r', encoding='utf-8') as f:
                self.loaded_refs[ref_name] = f.read()
        return self.loaded_refs[ref_name]
    
    def execute_opening(self):
        # 只在开局时加载这两个
        opening_flow = self.load_reference("开局流程.md")
        character_design = self.load_reference("角色设计.md")
        # ... 使用它们
    
    def save_state(self):
        # 只在存档时加载这个
        state_summary = self.load_reference("状态总结.md")
        # ... 使用它
```

### 6. 响应时间预算

#### 目标响应时间

- 普通回合：< 5 秒
- 深度校准回合：< 8 秒
- 开局（含流式反馈）：< 45 秒
- 存档输出：< 3 秒
- 状态查询：< 1 秒

```
系统: ⚙️ 正在塑造人物关系...
```

总耗时相同（可能稍短），但用户感知到系统在持续工作，焦虑感降低。

## 注意事项

1. **不改变输出格式**：进度提示只是额外的反馈，最终输出格式不变
2. **不暴露后台**：进度提示用自然语言，不暴露步骤号、字段名、脚本名
3. **不增加总耗时**：并行化可能减少总耗时，但流式反馈本身不增加耗时
4. **保持原子性**：开局仍然一次回复完成，进度提示只是中间反馈
5. **向后兼容**：优化不改变存档格式或状态模型
