# 开局流程

## 0. 本文件管什么

本文件是开局的维护与排错手册，不是模型每局必须逐段阅读的执行清单。生产开局的唯一入口是 `build_opening.py --complete`；参数、素材、状态结构和机器校验分别以脚本、`scripts/data/`、`references/状态总结.md` 与 `scripts/validate_state.py` 为准。本文件负责解释它们如何组成一次开局，并提供流程索引与故障定位入口。

本文件只管开局；其余归四个邻居文件：

| 文件 | 管什么 |
|---|---|
| `SKILL.md` | 命令语义、玩家叙事主权、回合事务、输出规范 |
| `references/角色设计.md` | 人物字段：起名、角色卡、双语态、亲密画像、配角 |
| `references/世界运转.md` | 时间、Tier 追算、事件、关系传播、压缩 |
| `references/状态总结.md` | v3 存档结构与保存检查、载入流程 |
| `references/加内容.md` | 扩充素材与文案的对照指南（维护时用） |

词条、权重和模板的运行数据在 `scripts/data/`，脚本不解析 Markdown。框架在 `authoring/frameworks/<ID>.yaml` 单独编辑，经 `python scripts/build_frameworks.py --write` 聚合到 `scripts/data/world_frameworks.yaml`；不手改聚合文件。维护职责与依赖看 `maintenance/data_manifest.yaml`，分级验证看 `references/加内容.md`。

## 1. 生产开局：唯一入口

### 1.1 命令与模式参数

能执行脚本时，生产开局只走这一条命令。世界、人物、事件和关系由脚本一次生成，不由模型逐步手填：

```text
python scripts/build_opening.py --complete --opening-mode daily [--session ID] [--framework auto|legacy|框架名称] [--seed N] [--lock KEY=VALUE]... [--slot 名称] [--force-table] [--all-custom] [--custom KEY=VALUE]
```

示例中的 `daily` 用于日常开局，压力开局替换为 `pressure`。

默认 `auto` 仅选来源哈希匹配且语义审查有效的框架；没有合格框架时明确失败，无隐式 `legacy` 回退。`--framework legacy` 是显式旧池入口；点名框架可以定向检查，但不等于取得默认抽取或发布资格。框架审查在 `maintenance/framework_reviews/`，核心池处置在 `maintenance/core_review_decisions.yaml`。

模式与六个透传参数一览（详细规矩见第 3 节对应小节）：

| 参数 | 干什么 |
|---|---|
| `--opening-mode pressure` 或 `--opening-mode daily` | 选择压力开局或日常开局；新局未选择时只展示选择项，不写状态 |
| `--seed N` | 指定随机种子，同种子必出同结果（见 3.3） |
| `--lock KEY=VALUE` | 预锁某个字段，可重复使用（见 3.2） |
| `--slot 名称` | 把本次开局存入指定命名槽 |
| `--session ID` | 显式指定稳定会话；省略时每次创建新 UUID，不由 seed 推导 |
| `--force-table` | 强制所有抽取值来自表内池（见 3.1） |
| `--all-custom` | 核心轴自拟但不解除框架约束；自由表外世界须显式配 `--framework legacy`（见 3.1） |
| `--custom KEY=VALUE` | 全自拟模式下逐项自定（只能配 `--all-custom` 用，见 3.1） |

### 1.2 运行后发生什么

新开局未指定类型时先询问“压力开局”或“日常开局”。载入、续玩和复用已有 `roll-file` 不重新询问；`seed` 或锁定素材本身也不等于已经选择模式。压力开局沿用完整压力与三层事件链；日常开局复用已登记的世界观、人物、处境和场景动作素材，但使用 `meta.daily_opening` 中的低压解释，不自动生成外部压力、near/far 事件或危机倒计时。

- stdout 打印三行进度和 `---opening_brief---` 块；模型只根据 brief 写玩家可见正文（分工见第 2 节）。
- 默认只写唯一工作档 `saves/sessions/<uuid>/state.yaml`，不共享全局活档；相同 seed 的两次新局仍是两个会话。
- 后台 brief 返回 `session`、绝对 `state_path`、文件原始字节 SHA256 `state_token`。宿主记录绑定，不把字段加入 v3 YAML 或玩家正文；自定义路径的 session 可为 null。
- 未给 `--seed` 时脚本用系统熵生成 0..2^31-1 的 seed；需要记录时用 `--request`，不要从会话 ID 推断 seed。
- 校验通过且要求的状态写入全部成功后才追加本局签名；输出已存在或状态写入失败不污染历史。历史只用于近期去重和素材冷却，重复只警告不拦（细则见 3.4）。

### 1.3 文件写入与覆盖

- 默认会话状态或 `--out` 指定的输出文件不覆盖；重建已有稳定会话须明确 `--force`。
- `--out <file>` 单独使用只写该文件；同时指定 `--session` 则另外写该会话工作档。`--working <file>` 保留显式工作路径兼容；`--no-working` 只写输出工件，没有 `--out` 时为 `saves/_opening_<seed>.yaml`。
- `--session` 不能与 `--no-working` 混用；与 `--working` 同用时须指向该会话的 state.yaml。后续按 brief 返回的路径操作，不推测默认路径。
- `--slot` 在状态文件生成后初始化命名槽。槽位失败不会回滚已经生成的状态文件，必须保留错误信息并按提示重试槽位操作。
- `--request` 只写调试用的开局请求摘要，不进入状态台账，也不替代状态文件。

### 1.4 其余参数

未在上面列出的参数——build_opening 的 `--roll-file` / `--out` / `--request` / `--check` / `--working` / `--no-working` / `--force`，以及 commit_turn / live_slice / manage_saves / validate_state 的全部参数——以各脚本 `--help` 为准。`fill_opening.py` 没有独立命令行入口。

## 2. 脚本、模型与 brief 的分工

### 2.1 脚本的内部顺序

`--complete` 由脚本完成结构抽取、状态构建、内容填充、校验、写入和 brief 输出。模型只依赖脚本成功输出的结果，不需要复现脚本内部顺序；`attraction.orientation` 由填料按角色背景自拟，全程不调用模型。

两条禁令：

- 模型不得单独运行 `roll_opening.py` 再填骨架；开局只从 `--complete` 这一个入口走。
- 素材填料或 `opening` 校验失败视为维护问题；参数、锁定值、文件已存在和槽位写入失败按第 8 节分类处理。生产开局不得由模型伪造整份 YAML 或用反复 `--check` 绕过失败；维护和测试可在明确用途下使用局部夹具或检查命令。

### 2.2 模型与 brief 的职责

根据 `opening_brief` 写已提交状态，不重新生成事实。仅新局依次使用 `世界观`、`人物`、`正文` 三个标题，前两项各 1-2 句。世界观选一条独特规则与地方细节；人物交代姓名、明确成年年龄、身份和眼前处境，命名不局限现代。正文从可接手的现场开始，不把前两项写成百科，也不泄露玩家未知的动机。载入与续玩不重复三个标题。

brief 里已经定好的事，模型不必也不该重做：

- brief 的 `unresolved` 来自 `current_node.unresolved_action`，已落在非交易靠近，除非玩家预锁了交易摊牌。
- 场景身份与边界：新建 `scene_id` 只标识当前场景；不创建场景许可账本。玩家硬边界由「本局不碰 X」命令在局内追加。
- 配角未进场时不生成完整配角卡。

### 2.3 brief 分层

- `opening_brief`：后台写作 brief；CLI 还携带 `session/state_path/state_token`，用于后续提交绑定。
- `opening_brief_compact`：玩家侧最小 brief，可由 `python scripts/live_slice.py <state> --compact` 输出；不含完整年龄、场景画像和世界常量，不能替代完整开局写作源或状态文件。
- 两种 brief 都不是新的状态来源；最终状态以绑定的 `state_path` 和 `validate_state.py` 为准。`--human`、`--compact` 是玩家侧输出，不提供完整后台绑定。

完整 brief 的关键来源：

| brief 字段 | 已提交状态与用途 |
|---|---|
| `player.age`、`npc.age` | 分别来自玩家与主要 NPC 的 age；人物介绍直接使用已确认年龄，不从身份或外观猜测，不补默认年龄 |
| `scene_profile` | 来自 `current_node.scene_profile`，提供场所可见度、出口等现场条件 |
| `situation` | 来自 `current_node.situation`，用于当前目标、未决选择、信息差和后果，不用 NPC 长期处境替代 |
| `world.constants` | 来自状态的 `world.constants`；框架的 `technology_boundary` 与有值的 `bridge_explanation` 已加入其中，约束开局及后续叙事 |

技术边界和桥接说明沿用 v3 现有常量列表持久化，续玩活切片的 `constants` 仍可读取，不新增 v3 字段，也不要求续玩重读框架源或自行补写解释。新局世界观介绍仍限 1-2 句，只选当前相关信息呈现，不把全部常量抄成设定清单。

### 2.4 正文红线

开局过程（骰子、角色卡、候选与评分、压力种子、校验过程）全部在后台执行，不向玩家展示；结构骰只服务后台生成。正文不得出现骰子、字段名、Tier 或任何校验过程痕迹。

## 3. 六个参数的详细规矩（查用区）

### 3.1 三种模式

- 默认 `table`：全部按解析后的表内池抽取。
- `--all-custom` 进入 `all_custom`：只允许脚本 `CUSTOM_KEYS` 中的核心规则、张力引擎、时代、地点、社会规则、压力来源、场景动作、身份族、处境和人物决策轴通过 `--custom KEY=VALUE` 自拟，其余轴仍由脚本抽取。`--custom` 不得脱离 `--all-custom` 单独使用；此模式下若仍有轴缺自定值（`custom_required`），脚本直接失败。
- `--force-table` 进入 `force_table`：与 `--all-custom` 互斥，禁止 `--custom`，所有锁定值必须来自解析后的表内池。

`--all-custom` 与框架选择是两项独立设置。默认 `auto` 仍只选已审框架；自拟核心规则、时代等若使所有已审框架都不兼容，脚本明确拒绝，不会静默回退。需要自由表外世界时，显式使用 `--framework legacy --all-custom` 并补齐所需 `--custom KEY=VALUE`；点名框架也不能借自拟值绕过该框架约束。日常模式限制和状态校验继续生效。

### 3.2 预锁 --lock

- `预锁 X=Y` 对应可重复使用的 `--lock X=Y`；锁字段只能来自脚本 `LOCKABLE_KEYS`，同一字段不可重复 lock；表内模式的锁定值必须存在于对应解析池。
- 压力模式的张力引擎是多值字段：写 `A` 表示锁定其中一项、另一项自动从池中补抽且互不相同；写 `A、B`（顿号或逗号分隔）表示锁定两项，两项不得重复；超过两项或含重复项会被脚本拒绝。
- 只有能对应 `LOCKABLE_KEYS` 的肯定约束才映射为 `--lock`（如「开局：当代，两个人对等」）；「不要职场」这类否定句没有 lock 键，不得假装已锁。

日常模式不补抽张力引擎，默认零项；预锁时只接受 `meta.daily_opening.张力引擎` 中的一项。核心规则、社会规则、处境与动作的锁定值须在日常登记中且符合时代/地点限制，否则明确报错。`--all-custom` 在日常模式中也不能绕过这些限制：未指定的这四轴由登记表补齐，压力来源留空，其余自定义必填轴仍遵守脚本要求。

### 3.3 种子 --seed

- `种子 N / seed=N` 对应 `--seed N`；N 必须是非负整数，未提供时由系统熵生成 0..2^31-1 的 seed。
- 确定性针对同版本素材和脚本下的结构抽取；需保持模式、锁、审查有效集与历史条件一致。会话 UUID、实际时钟和文件字节 token 不由 seed 固定，不能用 seed 代替会话绑定。
- 后台记录 `opening_request` 至少含 seed、protocol_version、mode、locks、custom、history 使用状态与校验结果；它不进台账、不进命名槽，需要时用 `--request` 另写调试文件。

### 3.4 防重复与防塌缩

防重复：连续开局的差异性由近期历史签名与「时代×地点×张力引擎」三元组共同辅助。历史文件在临时目录按工作副本隔离，最多保留 200 条；可用 `ADULT_TENSION_HISTORY_PATH` 明确指定位置。重复只发 warning，不阻断开局；失败不会追加一次成功开局记录。工作副本历史与每局独立的会话工作档不是同一种隔离。

防塌缩（表内模式、字段未被预锁时；名单数据在 `pools.yaml` 的 meta 节）：

- 不得把杠杆型引擎（meta.leverage_engines，现为「债务压力、秘密暴露倒计时、第三方施压、双重马甲互掉现场」）中的两项叠在同一局。
- `player_high` 不得默认给主 NPC 配杠杆处境（meta.situation_leverage，现为「债务压身 / 秘密将破 / 时限临门」）。
- 时代与地点冲突时按 `meta.location_eras` 和解：表抽值时代让路（硬锁地点是稀缺签）；玩家预锁/自拟值不让路，仅脚本 stderr 提示。
- 美学基调按 `meta.aesthetic_eras` 与时代做兼容检查：默认抽取时重抽明显跨域组合；玩家预锁或表外自拟时保留，并标记为需要在 `opening_brief` 中解释来源的世界观桥接。
- 场景动作默认抽「非交易靠近」。
- 身份族按 meta.identity_weights 的权重抽取（现行设计降低权力/商业、提高医疗/手艺/家族/艺术）。
- 玩家化身抽称谓、年龄段、社会位置，禁止默认「先生 + 三十余岁精英男 + 握着对方制度杠杆」。

### 3.5 其他开关与维护模式

- `--format json` 只改变输出格式。取值域勿混用：`roll_opening.py` 是 `text|json`；`commit_turn.py` / `live_slice.py` 是 `yaml|json`。
- `--twist` 不生成完整结构骰，改为抽取 2-3 个转折方向即退出；只在第一次跨天且 `meta.simulation` 为 true 时掷一次，经 `events_add` 与 `twist_generate: {reason: first_cross_day}` 落地。玩家明确要求新转折时使用 `reason: player_requested`，不得覆盖旧事件。
- `--no-history` 仅是 `roll_opening.py` 的维护参数，不是 `build_opening.py` 参数。无状态、无历史副作用的结构抽样使用 `sample_materials.py`；`build_opening --complete` 即使带 `--out`/`--no-working`，成功后仍追加历史。
- 维护专用，禁止用于生产开局：骨架模式（不带 `--complete` 的生成）与 `--check` 仅限维护/测试自检，不得产出可玩状态或绕过 `opening` 校验；直接运行 `python scripts/roll_opening.py` 同样仅限维护自检。

## 4. 素材从哪来，各自管什么

### 4.1 数据本体

运行数据在 `scripts/data/`；核心池编辑后同步登记，框架编辑源在 `authoring/frameworks/`，构建后才进入聚合文件。执行 `python scripts/qa.py --changed` 检查影响范围；结构通过不等于语义通过，也不等于完成真实模型实玩。

| 数据文件 | 装什么 |
|---|---|
| `pools.yaml` | 开局 12 张素材表（核心规则/美学基调/权力结构/张力引擎/时代与地点/社会规则/压力来源/场景动作/身份侧/处境侧/反差轴/玩家化身轴）＋ meta 行为开关（杠杆名单、死线名单、写实门控、身份族权重、地点时代和解表） |
| `character_meta.yaml` | 人物决策三轴、生成倾向权重、配角功能、年龄段区间、社会位置关系起点 |
| `twists.yaml` | 中期转折池（固定七类） |
| `templates.yaml` | 开局文案模板：开场句式、处境五句、撤回信号、压力反应、反差台词、吸引取向、建议动作 |
| `identities.yaml` | 身份族 → 具体身份（资源/限制/暴露风险），社会位置 → 玩家身份 |
| `locations.yaml` | 地点 → 具体房间/时段细节（每个地点至少一条） |
| `location_profiles.yaml` | 地点族的隐私、可见度、出口、见证者、可用行动和压力修饰 |
| `names.yaml` | 起名用姓氏与名字池 |
| `character_pools.yaml` | 角色三池：表层风味/口癖/外观与气质轴（≤8 字约束与写实门控键名见文件头注释） |
| `action_categories.yaml` | 非交易场景动作的功能分类 |
| `action_metadata.yaml` | 场景动作分类的功能、可见度和升级度元数据 |
| `identity_profiles.yaml` | 身份族的行为画像：谈判、冲突、修复、跟进、退出和证据习惯 |
| `twist_profiles.yaml` | 七类中期转折的影响范围、升级度、退出机会和第三方介入画像 |

### 4.2 setting_shell 四字段出处

开局先确定 `opening_mode`：`pressure` 维持完整压力链，`daily` 复用旧素材但不自动制造危机。`type` 与 `place` 来自 pools.yaml「时代与地点」（步骤 2），`rule` 来自「社会规则」（步骤 3），`pressure` 来自「压力来源」（步骤 4）。始终保留四字段映射，`type/place/rule` 非空；压力模式的 `pressure` 非空，日常模式固定为空字符串；「表外全随机」允许对应字段自拟，但不接受一句话字符串。

### 4.3 素材语义（为什么是分层的）

以下是压力模式的分层，日常模式不沿用这套强制压力链。三张压力表各管一层，不许合并：**张力引擎**＝整晚的戏路（恒抽两条）；**压力来源**＝今晚进门的现实由头；**处境侧**＝她本人正扛着的那件事。同名不同层的词（债务压力／债务到期／债务压身）是分层设计，不是抄重。

其余各表的分工：

- **场景动作**：分「交易摊牌」「非交易靠近」两桶；未决动作默认取后者，玩家预锁交易摊牌时才用前者。
- 非交易动作先由 `action_categories.yaml` 归入功能类别，再从 `action_metadata.yaml` 取得功能、可见度和升级度；这些信息进入当前节点，供模型判断普通回合的处理方式。
- **身份侧**：只回答「这个人凭什么能做什么」，必须能解释资源、限制与社会风险；具体身份模板在 `scripts/data/identities.yaml`。
- 身份族的行为倾向由 `identity_profiles.yaml` 接入身份档，只提供默认方向，不替代当前目标、知识、关系和 NPC 自主判断。
- **处境侧**：只决定角色正在承受的压力，不决定服从或许可。
- **反差轴**：只落入性格层与相处质感，不新增存档字段，不反推亲密画像或许可。
- **玩家化身轴**：只约束称呼、年龄观感和社会位置，不锁定性别或职业细节；抽中「学长」「学姐」或校园/师生意象时，须声明为成年人教育、职业培训或成年社群。

## 5. 四阶段开局流程

生产开局按四个阶段理解，不要求模型逐步参与。脚本按所选模式生成对应产物，1-14 仅为维护索引；任一阶段失败都停止在后台，不进入正文。

| 阶段 | 工作内容 | 主要产出 | 对应校验 |
|---|---|---|---|
| A. 抽取世界与模式 | 抽核心规则、美学基调、权力结构、时代、地点、社会规则；压力模式再抽压力来源与张力引擎 | 世界壳、世界常量；压力模式另有压力种子 | C1-C3（按模式） |
| B. 填充人物 | 生成玩家化身、主 NPC 年龄身份、处境、角色卡和自主冷却 | `player`、`npcs[main]` | C4-C8 |
| C. 建立可玩现场 | 压力模式落实 immediate/near/far 事件，日常模式保留空事件队列；两者均建立当前节点、场景身份、退出通道和已进场配角 | `events`、`current_node`、`scene_id`、配角 | C9-C12 |
| D. 落档与发布 | 建立顶层关系图，执行安全检查和开局校准，写入状态并生成 brief | `relationships`、`validation`、checkpoint、`opening_brief` | C13-C15 |

### 5.1 1-14 步骤对照附录

以下表格只用于维护排错和检查产出，不是第二套执行入口。压力相关产物只在压力模式生成，日常模式按下表例外处理；模型不手填其中任何字段。「会被盯的检查」一列指出该步产出对应的校验项。

| 步骤 | 名称 | 规则 | 产出 | 会被盯的检查 |
|---|---|---|---|---|
| 1 | 世界壳与核心规则 | 抽核心规则、美学基调、权力结构；压力模式抽 2 项互不相同的张力引擎；日常默认零项，可预锁一个低压方向 | `meta.power_structure`、`world.tension_engines`；核心规则进入 `world.constants`，美学基调作为第 4 条常量追加进 `world.constants`（「<美学基调>的质感贯穿这一夜…」） | C2 |
| 2 | 时代与地点 | 抽时代、地点 | `setting_shell.type`、`setting_shell.place` | C1 |
| 3 | 社会规则与世界常量 | 抽社会规则；把步骤 1-3 抽中的规则类项写成世界常量（至少 1 项） | `setting_shell.rule`、`world.constants` | C1、C2 |
| 4 | 压力来源与三层压力种子 | 压力模式抽压力来源并建立三层种子；日常模式的 pressure 与 immediate 为 ""，near/far 引用为 null | `setting_shell.pressure`、`world.pressure_seeds`、事件占位（压力模式） | C3 |
| 5 | 玩家化身 | 预锁姓名只做合规与去重；未预锁按 `references/角色设计.md` 标准起名；生成化身卡 | `player` 全部字段、`boundaries` 初始为空列表；玩家硬边界经「本局不碰 X」命令维护 | C4 |
| 6 | 主 NPC 标准起名 | 对应角色设计 9a 的起名半步：`name_profile`、≥3 候选、排除、选定、`naming_audit`；checks 任一 fail 即不合格。姓名审计与最终姓名必须同时写入该 NPC，不得只在开局过程留候选 | `naming_audit`、姓名字段 | C5 |
| 7 | 主 NPC 年龄与身份 | 对应角色设计 9a 的其余半步：年龄≥18 且明确；按身份族补具体身份、公开身份与身份档；身份档必须能解释资源、限制和风险 | `age`、`identity`、`identity_profile`、公开身份（`identity_profile.role`） | C6 |
| 8 | 主 NPC 处境档 | 按处境类型补齐触发、目标、未决选择、信息差、退出通道、后果与局势句；日常开局的压力为空、期限为 null，压力模式按模板填写；处境不得推导服从或许可 | `situation` | C7 |
| 9 | 主 NPC 全维角色卡 | 完成 9c-9g：决策三轴与可选反差轴、亲密画像核心子集、对玩家初始关系值与原因、语言滤镜与双语态、生成清单八项、`decision_card` 与自主冷却初始值。所有关系值只落在步骤 14 的顶层关系图 | main NPC 其余字段、`autonomy` | C8 |
| 10 | 开场三勾与事件队列 | 日常模式保留 `events: []`；压力模式把步骤 4 的三层压力落成事件：immediate、near、far（far 必 `hook: true`）；每项均带稳定 ID、唯一 `semantic_key`、非空 `source` 和可恢复的 `due_at`（无固定时间则为 null） | `events` | C3、C9 |
| 11 | 当前节点与未决动作 | `location`、`participants`、`situation`、`last_committed_result`、`unresolved_action`（停在玩家可接手处；可抽「场景动作」作未决动作类型）、`natural_next_pressure`（日常开局为空）；`location` 必须与当前场景一致 | `current_node` | C10 |
| 12 | 场景身份与退出通道 | 新建与 `current_node.location` 对应的 `scene_id`；确认 `safety_state: running`、`exits` 可用。后续地点、场景或参与者变化均须更换 `scene_id` | `current_node.scene_id`、`exits` | C11 |
| 13 | 配角 | 功能确认 → 配角简起名 → 核心价值与压力策略 → 其余字段（`references/角色设计.md`「配角」）；实际进入亲密线前先升为 `important_supporting` 并补齐规定字段 | `npcs[supporting…]` | C12 |
| 14 | 顶层关系图落档 | 为 player↔各 NPC 建边；多名 main 之间的关系一并生成；9e 初始关系值与原因以顶层边的 `trust`、`type`、`channel` 及相关人物记忆共同表达，不在人物卡覆写 | `relationships` | C13 |

注：

- 步骤 6-7 与步骤 9 提到的 9a、9c-9g 都是 `references/角色设计.md`「主 NPC 全维角色卡」下的编号条目（6-7 拆开只为校验）；步骤 5、13 的起名要求分别见同文件「玩家化身」「配角」。具体身份/地点细节由 identities.yaml / locations.yaml 提供（见第 4 节）。
- C14（安全项）与 C15（开局校准）是全局检查，不对应单个步骤。

## 6. 单次开局校验（C1-C15）

这张清单由 `build_opening.py --complete` 在 `opening` profile 校验环节自动执行，下表是各项通过标准，供排错时逐项对照。四阶段完成后、进入正文前执行；任一失败即 `validation.passed: false`，不得进入正文。条件项不适用时由排错记录写明原因，不要求把「—」写入状态字段。

| 编号 | 检查项 | 通过标准 |
|---|---|---|
| C1 | 世界壳 | `setting_shell.type/place/rule` 非空，pressure 为字符串；日常开局 pressure 为空 |
| C2 | 常量与引擎 | 两种模式均要求 `world.constants` 非空；压力模式要求至少两个张力引擎，日常模式允许 0-1 个已登记低压方向 |
| C3 | 压力种子 | 压力模式要求 `pressure_seeds` 齐全且 near/far 引用存在、kind 匹配、far 为 hook；日常模式允许压力为空且无开局事件引用 |
| C4 | 玩家化身 | 年龄≥18 且明确；姓名、身份、基线、名声非空；资源与知识可用；`player_naming_audit.chosen` 与 `player.name` 一致 |
| C5 | 主 NPC 起名 | `naming_audit.checks` 全部 pass；候选≥3、`chosen` 非空，且 chosen 与正式姓名字段一致 |
| C6 | 主 NPC 身份 | 年龄≥18 且明确；`identity_profile` 字段补齐 |
| C7 | 处境档 | 字段齐全、局势句成立 |
| C8 | 9c-9g | 三轴、可选反差轴、亲密画像核心子集、双语态、决策卡、9g 八项与自主冷却初始值齐全 |
| C9 | 开场事件 | 日常开局默认空队列；压力开局 immediate/near/far 事件齐全，hook 语义正确；每个事件有唯一 ID/`semantic_key`、非空 `source` 与合规 `due_at` |
| C10 | 当前节点 | 字段齐全；`unresolved_action` 停在玩家可接手处；`current_node.location` 与当前场景地点一致 |
| C11 | 场景身份 | `scene_id` 非空并标识当前地点与参与者；不生成或继承场景许可账本 |
| C12 | 配角 | 已进场的每名配角功能、简审计合格、必存字段齐全；已入亲密线者均已升级为 `important_supporting`。配角未进场时写「—（未进场）」 |
| C13 | 关系图 | player↔各 NPC 有边；多名 main 之间已生成；人物卡不存在覆盖顶层 `relationships` 的关系数值 |
| C14 | 安全项 | 全部角色年龄≥18 且明确；无 active 边界被场景违反；`safety_state: running` |
| C15 | 开局校准 | 已完成一次深度校准；提交后可见 `last_full_turn: 1`、`next_full_turn: 6`（即 last+5）、`force_full: false`、`force_reason: null` |

「深度校准」「last_full_turn」等字段的运转规则见 `SKILL.md`「每回合事务」的深度校准说明。

## 7. 校验通过后的发布

按顺序做四件事：

1. 把 `validation.passed: true` 记入后台 `opening_request`。
2. 从完整 `opening_brief` 提取四类玩家应知信息：世界初步印象、玩家为何在此、NPC 当前处境、现场可接续动作。
3. 按 `SKILL.md`「完整开局」依次输出 `世界观`、`人物`、`正文` 三个标题，前两项各 1-2 句；固定标题不固定正文措辞。仅新局如此，载入与续玩不重复。开局提交点即回合 1，`meta.turn` 是唯一回合号。
4. 新局不得写入 `directives`。

正文只需让玩家获得第一印象并知道下一步能做什么。不要展示 seed、字段名、候选姓名、结构骰、校验过程或后台 brief 原文。

## 8. 失败分类与恢复

按错误来源处理，不把所有失败都归为填料 bug：

| 错误类型 | 常见信号 | 处理 |
|---|---|---|
| 参数或锁定值错误 | `--lock`、`--custom`、模式互斥、seed 非法 | 修正输入后重新执行；不改状态文件 |
| 素材或填料错误 | `FillError`、固定素材缺失、无法组成角色或事件 | 停止开局，交给维护者修复素材或脚本；禁止模型手填 YAML |
| 状态校验错误 | `opening` profile 未通过 | 保留错误路径和校验结果，修复维护代码后重跑；不得进入正文 |
| 输出文件错误 | 文件已存在、路径不可写、编码或读取失败 | 不追加历史；默认不覆盖，更换路径或明确使用 `--force`。若一份状态副本已写出，保留核验，不声称全部回滚 |
| 命名槽错误 | 状态文件已生成但槽位初始化失败 | 保留已生成状态文件，单独重试槽位操作；不要重复掷骰生成另一局 |
| 历史辅助错误 | 无法读取或写入近期历史 | 允许开局继续，但记录 warning；历史只影响去重提示，不改变状态有效性 |

开局失败时不生成玩家可见正文。若状态文件已经写入，先确认其校验结果和用途，再决定是否初始化槽位或另存。

## 9. 维护与人工兜底

以下内容只用于维护、自检或脚本确实不可用时的人工兜底，不属于生产开局入口：

- 骨架模式、不带 `--complete` 的生成、`--check` 和直接运行 `roll_opening.py` 只用于维护或测试自检，不得产出可玩状态。
- 只有确实无法执行脚本时才手工抽取；各参数语义仍按第 3 节理解，词条清单直接读 `scripts/data/` 下的 yaml（见第 4 节）。
- 人工兜底必须明确标注为非脚本生成，不得声称获得协议版本（`opening-roll/v3`）、近期历史签名或脚本的随机映射。
