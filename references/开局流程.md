# 完整开局流程

本文件是新开局的唯一流程源，规定执行顺序、结构骰协议、素材落成方式、开局校验与原子落档。

## 引用与字段约定

- 抽样表只在 `references/素材库.md` 维护；脚本骰成功时无需读取该文件。
- 人物生成、起名、身份档、处境档和角色卡结构只在 `references/角色设计.md` 维护。
- v3 存档结构、同意记录与保存检查只在 `references/状态总结.md` 维护。
- 玩家可见输出、安全不变量、玩家叙事主权和每回合事务只在 `SKILL.md` 维护。
- 本文件的结构种子默认落入上述既有字段；仅显式给出 YAML 结构时才建立该结构，不为临时生成轴新增存档字段。

## 完整开局规则

1. 新开局必须完整执行步骤 1-14，再生成玩家化身、三层压力种子、开场三勾和当前节点；不得简化为少量种子。
2. 默认采用“表结构末位自拟”：每个结构表在表内选项之外增加一个“系统自拟”末位。玩家说“强制表内”时取消末位；玩家说“表外全随机”时仍完整执行全部步骤，但核心规则、引擎、壳、动作、身份、处境和人物决策轴改为自拟，其他轴照常抽取。
3. 玩家限定题材时只锁定大类；细分轴仍逐轴抽取。预锁字段和玩家边界不可被抽样、修复或“更有故事感”的替代项改写。
4. 非锁定的结构骰结果允许根据已生成内容做小幅改写以保证咬合，但不得对同一骰位二次重挑结果；微调只调整已选项的表述或细节，重挑是换一个候选。
5. 角色年龄与成年教育表述按 `references/角色设计.md` 执行；开局安全校验按 `SKILL.md` 不变量执行。

### 模块边界

同一事实只在一个模块中成为正式字段，其他模块只能引用，不能重复改写。例如身份侧保存“权限来源”，处境侧只描述该权限此刻是否够用。

| 模块 | 对应步骤 | 只负责 |
|---|---:|---|
| 世界观档、核心规则与基调轴 | 1 | 可用素材、改变日常的规则和本局质感 |
| 张力引擎 | 2-4 | 哪项矛盾正在变贵，以及双引擎如何咬合 |
| 制度与场合壳 | 5 | 一个地点、一条当前规则和一项压力 |
| 开场动作 | 5 | 人物此刻共同在做什么，以及尚未完成的动作 |
| 身份侧 | 9、13 | 角色凭什么拥有资源，以及受什么限制 |
| 处境侧 | 9、13 | 角色为什么现在必须行动 |
| 人物生成 | 9-13 | 身体、人格、亲密画像和决策规则 |
| 因果网络 | 10、14 及附加生成 | 把角色选择转化为关系、事件和后果 |

## 1-14 开局流程

下表是步骤名称、顺序、规则、产出与完成度键的唯一来源。条件不适用时必须显式写 `—` 和原因。

| 序 | 完成度键 | 项目 | 规则 | 产出 |
|---:|---|---|---|---|
| 1 | `s1_world_tone` | 世界观档、基调、核心规则与开场时景 | 档位 1..3；逐轴抽取基调和核心规则；限定题材时先应用兼容档位，再加抽大类细分轴；时景只作氛围建议 | 档位 + 基调卡 + 一句世界常量 + 开场时景建议 |
| 2 | `s2_engine` | 主张力引擎 | 9 个核心族之一与族内具体项（`素材库.md`「张力引擎」） | 一句可演压力 |
| 3 | `s3_mesh` | 咬合开关 | 范围 1..2 | 单引擎 / 双引擎 |
| 4 | `s4_sub_engine` | 副引擎（对冲） | 仅双引擎时生成，族不得与主引擎相同 | 第二条压力；单引擎写 `—` 及原因 |
| 5 | `s5_shell` | 制度与场合壳、开场动作 | 分别抽壳类和动作族；壳给地点/规则/压力，动作给正在进行和尚未完成的行为 | 壳结构 + 动作种子 |
| 6 | `s6_tier` | Tier | 范围 1..3 | 世界追算深度 |
| 7 | `s7_mode` | 模式 | 范围 1..2 | `reliable` / `immersive` |
| 8 | `s8_power` | 权力结构 | 范围 1..4 | 玩家高位 / NPC 高位 / 对等 / 可切换 |
| 9 | `s9_main_npc` | 主 NPC 全维 | 每名主 NPC 独立执行 9a-9g 并抽人物决策三轴；9a 先完成标准起名。后宫/群像局以 `--mains N` 生成多名主 NPC | 每名主 NPC 的完整角色卡 + 合格 `naming_audit` |
| 10 | `s10_relation_stage` | 关系阶段与安全字段 | 可抽 `素材库.md`「关系阶段」；单向暗恋另抽方向；同意初始值不得由关系阶段推导 | 关系阶段、初始同意记录、撤回信号 |
| 11 | `s11_cast_count` | 配角数 | 范围 1..3 | 数量 |
| 12 | `s12_cast_roles` | 配角功能 | 每人独立生成 | 功能列表 |
| 13 | `s13_cast_cards` | 配角建档 | 每人先简起名，再抽核心价值与压力策略并完成建档 | 配角卡 + 简 `naming_audit` |
| 14 | `s14_relation_graph` | 关系图 | Tier 3 必须生成；其他 Tier 可按剧情需要生成 | 以稳定角色 ID 为端点的关系边；不适用时写 `—` 及原因 |

步骤 9 存在多名 `main` 时，只有每名主 NPC 都完成 9a-9g、各自具备合格标准 `naming_audit`，且彼此姓名和读音不冲突，`s9_main_npc` 才可记为 `done`。

步骤 10 的同意记录按 `references/状态总结.md`「同意记录」建立。没有明确许可时保留 `unknown` 或空 `grants`，不得因关系阶段、身份、吸引或处境自动写成 `granted`；撤回信号写入 NPC `withdrawal_signal`，许可判定仍以 `SKILL.md` 为准。

完成 1-14 后继续生成玩家化身（`references/角色设计.md`「玩家化身」）、三层压力种子、开场三勾和当前节点。玩家姓名按「名字生成与去重」处理；预锁姓名只做合规与去重。

存档枚举使用英文：玩家高位=`player_high`、NPC 高位=`npc_high`、对等=`equal`、可切换=`switchable`；可靠=`reliable`、沉浸=`immersive`。

## 随机性与多样性协议

语言模型没有真随机，默认会挑“最顺手”的表项，导致同一题材下开局趋同。结构骰分两类，全部按本协议执行：

- **表骰**：从素材表抽行的骰——世界基调与核心规则各轴、季节与时景各轴、大类细分各轴、引擎族与族内项、壳类、开场动作、身份族与身份种子、处境类型、人物决策轴、关系阶段、反差轴、配角功能、表层风味、口癖。
- **范围骰**：小范围整数骰——世界观档 1..3、咬合 1..2、Tier 1..3、模式 1..2、权力结构 1..4、配角数 1..3。

1. **脚本骰优先**：运行环境能执行脚本时，先运行 `python scripts/roll_opening.py`。可用参数为 `--seed N`、`--genre 大类`、`--lock 字段=值`、`--no-custom`、`--all-custom`、`--no-history`、`--mains N`、`--twist`；仅查题材时用 `--list-genres`。直接采用脚本输出作为全部结构骰结果，跳过第 2、3 条的手工抽取，且无需读取 `素材库.md`。仅当某项与预锁或已生成内容明显不成立时，自拟一个同类替代或重跑一次脚本。在 `validation.checklist.notes` 记录 `dice_source: script`。脚本不可用或报错时退回手工抽取并加载 `素材库.md`，记录 `dice_source: protocol`。
2. **表骰先枚举后选择（手工时）**：每个表骰先在内部列出 `min(5, 表长)` 个候选，候选尽量来自 3 个不同族/行；再从中选择与已锁定要素咬合最紧、且最近可见对局未用过的一项。禁止直接取表格首行、该题材最著名的选项，或每次都挑同一“最有趣”的选项。
3. **范围骰不取惯性值（手工时）**：在合法范围内自由取值，禁止总取中间值、默认值或与上一局相同的值。
4. **范围只锁大类**：玩家限定题材范围（如“末世”“修真”）时，只锁定大类；`素材库.md`「大类细分轴」仍须逐轴重新抽取。禁止把题材刻板组合（如末世＝丧尸＋避难所＋压抑求生）当默认结果。
5. **跨局覆盖感知**：脚本把世界档、核心规则、题材、引擎、壳、动作、身份、处境、关系阶段和人物决策轴写入根目录 `.opening_history`（运行态，不入库），只保留最近 30 条；无 `--seed` 时比较 16 个候选，优先选择单项和关键配对较少重复者，并硬避最近 5 局的“引擎族×壳类×身份族”原组合。旧三项历史可直接读取。`--seed N` 跳过历史以保证复现；`--no-history` 关闭历史读写。手工抽取时同样优先使用近期少见的单项和配对。
6. **seed 映射（手工后备）**：对第 `k` 个结构骰，取表内第 `(N + k) mod 表长` 行；`k` 按步骤 1-14 的顺序计数，同一步骤内按轴顺延，行号从 0 起。命中预锁项、明显不成立项或不适用的“系统自拟”末位时，向下顺延一行。seed 只约束结构骰，不约束文本细节。脚本可用时直接传 `--seed N`，不执行手工映射。
7. **锁定项除外**：预锁字段和玩家边界不参与本协议，也不得以“换个更有趣的”为由改写。非锁定项按「完整开局规则」第 4 条只可小幅微调，不可二次重挑。

手工抽取表骰前必须实际读取 `references/素材库.md` 的对应表；表层风味、配角功能和画像倾向表位于 `references/角色设计.md`。不得凭记忆虚构表项。候选、理由和映射计算全部留在后台。

## 素材使用规则

本节只规定结构骰结果如何落成正式字段。身份与处境的字段结构见 `references/角色设计.md`「身份档」「处境档」。

### 世界观档（步骤 1）

世界观档决定世界规则，Tier 只决定追算深度。先确定世界观档，再按下列规则加载素材增补：

| 档位 | 基础规则 |
|---|---|
| 现实 | 资源、身份、身体和制度遵循现实逻辑 |
| 半架空 | 保留现实社会，只加入一层异常规则、能力或特殊机构；使用通用池 + 半架空增补 |
| 强架空 | 世界法则、种族、契约、力量和社会制度均可不同；使用通用池 + 强架空增补 |

现实档不得加载增补；半架空与强架空增补不得混用。通用池不得包含依赖异常、异界、系统或超自然前提的素材。预锁项与世界观档冲突时停止开局；若玩家同时预锁现实档和 `素材库.md`「现实档排除」中的禁用项，同样停止掷骰并报告冲突。增补只改变世界规则和素材范围，不改变年龄、玩家控制权或场景许可。强架空中的契约、血统、命运和阶位不能替代角色拒绝或同意。

### 世界基调卡（步骤 1）

确定档位后逐轴抽取世界基调。每轴独立，允许反差组合（如末世×温柔日常、宫廷×黑色幽默）。玩家限定题材时加抽大类细分轴；未收录的大类比照该节自拟细分轴后逐轴抽取。

美学基调只影响画面质感、比喻系统、对白口吻和表层风味的可用池，不改变安全不变量、许可判定或 `SKILL.md` 的性行为场景写法标准。玩家点名时预锁该风格；未指定时与其他轴一样抽取。

```yaml
world_tone:
  era_tech: null
  region: null
  society: null
  narrative_tone: null
  aesthetic: null
```

世界基调卡只作为 `world.constants` 和开场渲染的生成来源，不另建 v3 顶层字段。

### 世界核心规则（步骤 1）

逐轴抽取“核心规则来源、掌握范围、生效代价、变化阶段”。先依据题材把来源具体化为可观察、可违反的规则，不得直接把类别名当设定；再合成为一句可验证的世界常量：

```text
在本世界，<具体规则>；其可用性或约束范围是 <掌握范围>，使用或违背它会付出 <代价>；
当前正处于 <变化阶段>，这使开场压力成立。
```

现实档只用通用池；半架空和强架空只加载各自增补。结果写入 `world.constants`。大类题材先按兼容标签限制世界观档，再对具体细分项执行现实档排除；兼容档位只负责题材级筛选，不代替具体表项过滤。

### 开场时景（步骤 1）

抽取 `素材库.md`「季节与时景轴」各轴，作为开场氛围与感官细节建议，融入【世界观背景】与【正文】。与世界设定明显不合时（如星际、异界），换用该世界的等价时景。时景不单独输出、不写入存档，也不另设完成度键；它随 `s1_world_tone` 一并核对。

### 张力引擎与咬合（步骤 2-4）

先选择 9 个核心族之一，再选择族内具体项。核心族只定义冲突来源，具体项负责把冲突落成可演事件。将结果翻译成“谁拥有什么、谁缺什么、什么即将改变”的一句压力，不能只输出标签。

双引擎必须形成因果连接：

```text
因为 <主引擎压力>，所以 <副引擎> 变得更昂贵或更危险。
```

### 制度与场合壳（步骤 5）

从壳表选择一种场所类型，再只补全一个具体地点、一条当前规则和一项压力。交易、契约、展演等机制由张力引擎和处境负责，不能反过来充当地点。

```yaml
setting_shell:
  type: null
  place: null
  rule: null
  pressure: null
```

```text
<场合类型>中的<具体地点>；
当前规则是<限制>，它让<人物/玩家>必须在<压力>下做选择。
```

`rule` 只写当前最有效的一条限制；`pressure` 必须说明它如何让至少一个开场选择更难或更贵。无关剧情的监控、权限、出口或条款不生成。壳只提供制度、场合与压力，角色态度仍按 `SKILL.md` 判定。

### 开场动作（步骤 5）

从动作母型选择“动作族→具体种子”，与壳、处境分别回答“在做什么、在哪里做、为什么必须现在做”。具体动作写入 `situation.trigger` 或 `immediate_objective`，尚未完成部分写入 `current_node.unresolved_action`。动作与壳明显不合时，只换成同族等价行为，不重抽世界。

### 脚本输出落档映射

`roll_opening.py` 只生成结构种子，执行者必须按下表转译，不能把标签原样堆入正文或另建字段：

| 脚本输出 | 落档去向 |
|---|---|
| 世界观档、基调、核心规则、时景 | 按本节步骤 1 规则具体化；时景只用于渲染 |
| 主/副引擎、咬合 | `world.tension_engines` 与三层压力事件 |
| 壳、动作 | `world.setting_shell`、NPC `situation`、`current_node.unresolved_action` |
| 身份、处境 | NPC `identity_profile` 与 `situation` |
| 人物决策三轴 | NPC 稳定核心、目标、压力反应和行动偏好 |
| 关系阶段、初始关系建议 | 顶层 `relationships`；9e 必须写出原因，建议值可在合法范围内小幅调整 |
| 画像倾向 | 只作为亲密画像生成权重，不落字段、不推导许可 |
| 反差轴、表层风味、口癖 | 9c 性格证据与 9f `voice_filter` |
| 外观 | 9g-1 外貌与识别细节 |
| 配角功能 | 配角 `function` 及其目标/位置安排 |

## 三层压力种子

1. 即时：本场已经可见的压力。
2. 近程：数回合内会触发的事件，建立稳定事件 ID。
3. 远程：长弧后果，建立远程钩子（`[钩]` 标记）和稳定事件 ID。

## 开场三勾（opening_hooks）

- 写出引擎咬合如何让选择变贵。
- 写出世界核心规则如何支撑 9b 的具体局势。
- 写出谁在哪里、正在执行哪种开场动作，以及尚未决定的部分。

三勾只用于后台组织开场，融入【故事背景】和【正文】，不单独输出、不作为 v3 存档字段。

## 开局事务流程

凡步骤 1-14 要求“建立稳定 ID”或“提交初始状态”，均延后到原子落档阶段；落档前只保留无正式 ID 的草稿。

### 五阶段流程

| 阶段 | 行为 | 写入正式状态 |
|---|---|---|
| 1. 读取要求 | 固化模式、预锁项、边界与种子 | 否 |
| 2. 生成草稿 | 完成 1-14、玩家化身、压力种子、三勾和当前节点 | 否 |
| 3. 开局校验 | 检查完成度、结构、因果、人物、安全、名字与重复度 | 否 |
| 4. 局部修复 | 只修错误字段，最多两轮；每轮后重新校验 | 否 |
| 5. 原子落档 | 一次性生成 ID、提交 v3 状态并渲染开场 | 是 |

### 1. 读取要求

```yaml
opening_request:
  mode: default
  locks:
    world_type: null
    setting_shell: null
    scene_action: null
    npc_identity: null
  player_boundaries: []
  seed: null
```

玩家明确指定的任意字段都加入 `locks`。预锁字段不可改写；组合困难时只能调整未锁字段。边界同样不可作为修复目标。`seed` 的执行方式以「随机性与多样性协议」为准。

### 2. 生成草稿

按步骤 1-14 依序生成，再生成玩家化身、三层压力种子、开场三勾和当前节点。各步起名时机与流程以 1-14 表和 `references/角色设计.md`「名字生成与去重」为准。结果只写入：

```yaml
opening_draft:
  world: {}
  player: {}
  npcs: []
  relationships: []
  events: []
  current_node: {}
  validation: {}
```

草稿期不得生成正式角色或事件 ID、推进时钟或回合、写入正式台账。互相引用使用仅在草稿期有效的临时键。`opening_draft` 不是 v3 存档，不得交给 `scripts/validate_state.py` 或用于载入。

### 3. 开局校验

初检后若有错误，进入局部修复；每轮修复后重新执行本节校验，最多两轮。

第一步逐项核对完成度。任何一项缺失、为空或既非 `done` 也非 `n_a`，一律 `passed: false`。`n_a` 只允许用于条件步骤 4 和 14，且必须在 `notes` 附原因。步骤 1-14 的键与判定以「1-14 开局流程」表为准；附加生成使用后三项键：

```yaml
validation:
  checklist:
    s1_world_tone: done
    s2_engine: done
    s3_mesh: done
    s4_sub_engine: done|n_a
    s5_shell: done
    s6_tier: done
    s7_mode: done
    s8_power: done
    s9_main_npc: done
    s10_relation_stage: done
    s11_cast_count: done
    s12_cast_roles: done
    s13_cast_cards: done
    s14_relation_graph: done|n_a
    player_avatar: done
    pressure_seeds: done
    opening_hooks: done
    notes:                              # 两类用途：记录骰源；为任一 n_a 附原因
      - "dice_source: script"
      - "s4_sub_engine=n_a: 单引擎，无副引擎"
  passed: false
  errors:
    - field: npcs[0].resources
      reason: 身份无法支持最高权限
      repair: 降低权限或为未锁字段补充合法来源
```

完成度通过后，再按以下层次检查完整草稿：

- 结构：1-14、附加生成、字段、人数、功能和关系边一致；多名 `main` 各自完整。
- 档位：现实、半架空和强架空的素材池与世界观档一致，无跨档增补混用。
- 因果：核心规则能解释世界压力；身份能解释资源与权限；远近事件有压力来源。
- 人物：决策轴落实为目标、底线或行为，知识、资源和压力反应兼容。
- 亲密：核心画像独立生成、无刻板绑定，关系阶段和吸引不自动扩大许可。
- 安全：按 `SKILL.md` 不变量校验；年龄、边界、同意和玩家控制权全部明确。
- 名字：每名主 NPC 和未预锁玩家通过标准审计；配角通过简审计；同局不重名、读音不冲突，配角更普通。
- 重复度与协议：身份组合、处境和标志细节不过度重复；限定题材时不退化为刻板模板；结构骰符合随机性协议；不得按“更有故事感”翻案未选中候选。

每条错误必须定位到字段，并给出不触碰预锁项和玩家边界的修复方式。无错误时 `passed: true` 且 `errors: []`。这里的 `validation` 只用于开局草稿校验；v3 存档错误由 `scripts/validate_state.py` 输出，两者不是同一格式。

### 4. 局部修复

每轮只修改 `validation.errors` 指向的字段及其直接依赖，禁止因局部问题重抽整个世界。修复顺序：

1. 年龄、边界、同意和玩家控制权。
2. 世界观档与素材增补、身份之间的冲突。
3. 目标、资源和事件冲突。
4. 人物知识越界。
5. 亲密画像绑定错误。
6. 起名审计缺失、重名/读音冲突、配角不够普通。
7. 文风、细节重复和刻板模板。

名字错误只允许重跑该角色起名或替换未锁姓名，不得借机重抽世界或亲密画像。预锁姓名只做合规与去重，不得改写。

每轮修复后重新校验，最多两轮。两轮后仍失败则终止开局，不得提交草稿或渲染正文；对玩家只用人话说明本次开局条件仍有冲突，并指出需要调整的预锁项或补充的信息，不展示后台字段、错误结构或校验步骤。

### 5. 原子落档

仅当 `validation.passed: true` 时一次性完成：

1. 生成全局唯一、稳定的角色、边界、同意、事件和关系引用 ID。
2. 将 `opening_request.player_boundaries` 与玩家化身明确声明的硬边界合并去重，写入顶层 `boundaries`，初始状态为 `active`。
3. 写入世界常量、张力引擎、壳、人物决策卡、合格 `naming_audit`、关系边、当前场景同意、三层压力事件和当前节点。
4. 提交内部回合 0，初始化世界时钟、NPC 自主冷却和 checkpoint，再按 `SKILL.md` 开局输出格式渲染（显示“回合：1”）。

落档是单次事务：任一必填字段、引用、起名审计、ID 或 v3 保存约束失败则整体回滚。无合格起名审计不得落档。落档后可在后台使用 `scripts/validate_state.py` 对完整 v3 状态执行保存检查；失败时不得输出伪存档或正文。

落档与渲染均不向玩家展示骰子、角色卡、起名候选/评分、`naming_audit`、压力种子、三勾、校验清单或内部台账；只有玩家明确要求“存档”时，才按 `references/状态总结.md` 输出可恢复 YAML。
