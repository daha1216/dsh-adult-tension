# 角色设计

本文件只负责人物层，分四部分：通用生成规则、命名、角色规格、角色类型与层级。执行时机、结构骰与开局校验以 `references/开局流程.md` 为准；身份与处境的语义见 `references/开局流程.md` 第 4 节；安全不变量以 `SKILL.md` 为准。

本文件**只承载语义**：条目数据（决策三轴、生成权重、配角功能、表层风味、口癖、外观轴）全部在 `scripts/data/character_meta.yaml` 与 `scripts/data/character_pools.yaml`，脚本不解析本文件，章节标题可自由调整。想改条目直接改 yaml，改完跑 `python scripts/check_content.py`；扩充方法见 `references/加内容.md`。

**成年底线**：主要角色和亲密互动参与者必须明确为 18 岁以上；校园、社团、学园或师生意象须声明为成年人教育、职业培训或成年社群。所有画像仅用于明确为成年人的虚构角色——知识少、经验少、单纯或不懂世事不得被解释为年龄不明或未成年。

**许可边界**：身份、处境、权力结构与把柄只解释资源、限制和压力，不自动构成亲密许可；处境、把柄、债务、职级差和死线不得折算为同意。许可判定只按 `SKILL.md`。

**章节导览**

- 第一部分 通用生成规则：人物生成原则（倾向权重）→ 可选修饰层（表层风味/外观轴/口癖）→ 人物决策轴（三轴种子）
- 第二部分 命名：名字生成与去重（分层要求 → 起名流程 → 审计结构与姓名字段）
- 第三部分 角色规格：主 NPC 全维角色卡（9a-9g 与 9g 生成清单）→ 身份档 → 处境档 → 亲密画像 → 表里双语态 → 角色决策卡
- 第四部分 角色类型与层级：角色层级与持久化（含普通配角升级规则）→ 配角 → 玩家化身

# 第一部分 通用生成规则

## 人物生成原则

先生成普通人格、目标、底线和生活处境。

倾向的用法：先抽一个宽泛倾向定大方向，再逐个字段落实。倾向只调概率，不锁死结果。

分工与底线：主 NPC 可以提高少见组合的出现机会；配角走自然普通路线。同一局里的人物，不许人人一种倾向。

倾向共八档，数据与权重在 `scripts/data/character_meta.yaml` 的「人物生成倾向」（权重总和必须为 100；现行设计里普通自然档权重最高）。改权重即改开局口味。

## 可选修饰层

以下修饰层均可选，共享同一组通则：

1. 只影响语言滤镜、画面质感、标志动作与相处质感，不改变人格、目标、底线、亲密画像或许可判定。
2. 同局不同角色不重复同一项；各修饰层与亲密画像分别独立抽取，互不推导。
3. 抽取遵循 `references/开局流程.md` 的结构骰协议。
4. 美学基调为写实档（名单见 `pools.yaml` 的 meta.gate_aesthetics，现为「青年漫写实」「写实文学」「工笔华服」「水墨写意」）时，表层风味与口癖跳过（写 `—`）；外观轴仍可用，但只取写实项。
5. 抽用量：主 NPC 或重要配角可各抽用下列三层；外观轴由脚本为主 NPC 恰抽两项、配角恰抽一项（全轴混合池，不保证分层分布），表层风味与口癖各至多一项。抽用结果写入 9f 语言滤镜或外貌细节，不新增存档字段。

三层条目数据同在 `scripts/data/character_pools.yaml`（单项 ≤8 字由加载器强制过滤），抽取时不先抽分组，分组仅用于检索、去重与生成解释：

- **表层风味**：按组组织，各组条目的并集即为池。
- **外观与气质轴**：轴→组→条目两层结构。现实档中的非自然发色瞳色写为染发、美瞳，或顺延为自然色；写实门控按名引用「自然发色」「瞳色」「异色瞳」这些键名（见文件头注释），故这些键名不可改名。
- **口癖与语感**：按组组织，各组条目的并集即为池。

## 人物决策轴

为主 NPC 逐轴抽取；配角只取核心价值与压力策略。它们是生成目标、底线和决策卡的种子，不新增存档字段，也不推导亲密画像或当前许可。

- **核心价值**：角色最在乎的那件事——落到稳定核心与首要目标。
- **压力策略**：压力上来时的习惯动作——落到压力反应与行动偏好。
- **关系姿态**：对人默认的距离——落到性格与行为证据。

三轴的条目清单在 `scripts/data/character_meta.yaml` 的「决策轴」（每轴至少两项）。同局角色尽量不重复同一组合。

三轴只是种子：落到哪里（核心价值→稳定核心/目标，压力策略→压力反应/行动偏好，关系姿态→性格与行为证据），统一写在「角色决策卡」，这里不重复；标签不许原样抄进人物介绍。

反差轴（条目在 `pools.yaml`，专属台词在 `templates.yaml`）只落进性格层和相处质感，不加字段，也不反推亲密画像或许可。

# 第二部分 命名

## 名字生成与去重

起名是开局关卡，不是润色：名字由生活背景决定，不由性格、欲望或反差设定决定。

三条禁令：不许跳过，不许事后补，不许先定人设/反差/画像再回头配名——没有合格姓名，就不写其他人物字段。

时机：主 NPC 在 9a 先完成标准起名再写年龄/身份；步骤 13 每名配角先简起名；玩家化身按下表处理。任何一处起名不合格，开局校验就不通过（`validation.passed: false`）。

### 分层要求

| 角色 | 流程 | 候选 | 审计深度 |
|---|---|---|---|
| 主 NPC | 标准起名 | ≥3 | 标准 `naming_audit` |
| 未预锁玩家化身 | 标准起名 | ≥3 | 标准 `naming_audit` |
| 预锁玩家姓名 | 合规与去重 | — | `locked_by_player: true` + checks |
| 配角 | 简起名 | ≥2 | 简 `naming_audit` |

### 起名流程

标准起名（主 NPC / 未预锁玩家化身）与简起名（配角）共用同一套步骤：

1. 建立 `name_profile`（culture / region / era / social_context / usage）；配角继承本局主文化/地区/年代，可只写精简 profile。
2. 生成候选（中文先姓后名再组合）：标准 ≥3 个、简 ≥2 个；配角的候选挑更常见、更容易区分的。
3. 排除同局重名、读音冲突、文化明显不符或象征意味过强的候选。
4. 在剩余候选中选择最自然、最符合角色生活背景且便于区分的姓名；不得按性格、外貌或“最有故事感”选名。
5. 写入 `naming_audit` 与姓名字段后，才继续写其余人物字段。

配角差异：选名不做分项评分，只求与同局不冲突、自然普通，且姓名必须比主 NPC 更普通。

> **对**：按角色的生活背景取普通人名，先列 ≥3 个候选再挑。
> **错**：因为人设冷艳就挑生僻花名；或者先把名字想得够帅，再倒回去凑人设。

### 审计结构

标准与简起名共用同一结构，用 `mode` 区分。机器校验只强制三件事：`chosen` 非空且与姓名一致、携带 `source` 与 `approved_turn`。

```yaml
naming_audit:
  role_ref: main_npc|player|supporting
  mode: standard|lite            # 主 NPC / 未预锁玩家 = standard；配角 = lite
  name_profile: {culture: null, region: null, era: null, social_context: null, usage: legal_name}
  candidates:                    # standard ≥3；lite ≥2
    - {name: null, reject_reason: null}
  chosen: null
  source: null                   # 机器校验必填（如 角色设计.md / 玩家提供）
  approved_turn: null            # 机器校验必填（开局为 1）
  checks:
    same_cast_duplicate: pass|fail
    phonetic_clash: pass|fail
    culture_match: pass|warn|fail
    natural_fit: pass|fail
    supporting_plainer: pass|fail|n_a   # 仅 lite 检查；standard 写 n_a
  recent_check: checked|unavailable
  locked_by_player: false
```

`checks` 是生成时的自评记录：手填路径任一项 `fail` 即该角色起名不合格，开局校验不通过；「候选 ≥3 / ≥2」同样只约束手填路径。

脚本路径（`build_opening.py --complete`）按现代都市名池（`names.yaml`）机械取名，不做多候选比选；非当代时代背景下 `checks.culture_match` 如实记 `warn` 而非 `pass`。

姓名字段 `legal_name` / `public_name` / `nickname` / `alias` 只填剧情需要的字段，`naming_audit.chosen` 默认写入 `legal_name`。以前局面的取名记录只用来查重，不能拿它改动玩家预锁的姓名。命名检查直接依据角色所在文化、地区、年代和社会背景，不依赖外部命名权重文件。

# 第三部分 角色规格

## 主 NPC 全维角色卡

### 9a-9g

| 子步 | 内容 |
|---|---|
| 9a | 标准起名后写入姓名、年龄（≥18）、身份（按「身份档」补齐）、公开名声。开局流程把本子步拆成步骤 6（起名）与步骤 7（年龄与身份），只为校验 |
| 9b | 处境类型、具体压力、局势句（按「处境档」补齐） |
| 9c | 人物决策三轴，再加可选反差轴（均不锁定亲密画像） |
| 9d | 亲密画像开局核心子集与变化基线 |
| 9e | 对玩家初始关系 −5..+5，并写出原因 |
| 9f | 语言滤镜：句长、礼貌度、回避方式、压力下口吻；抽取了表层风味时须在此体现；进入亲密线的角色按「表里双语态」补齐两档 |
| 9g | 生成清单核对（索引，不重复写内容） |

9a 先完成标准起名再写其余字段，时机与禁令统一见「名字生成与去重」；无合格姓名不得进入 9b。

### 9g 生成清单

作为核对索引，确认结果已存在即可，勿再生成第二套卡。以下核对项已在 9a-9f 或引用结构中产出，此处只核对不重写：

- 9g-1 外貌与识别细节（可抽外观轴）
- 9g-2 核心性格与三轴表现（9c）
- 9g-3 目标与利害（9b/决策卡）
- 9g-4 底线与拒绝方式（决策卡）
- 9g-5 语言滤镜与双语态（9f）
- 9g-6 亲密画像与变化基线（9d）

9g 只需显式补齐下列尚未在别处产出的八项：

1. 标志动作
2. 已知 / 未知信息
3. 近期记忆 1-2 条
4. 当前情绪
5. 资源与把柄
6. 地点与行动窗口
7. 亲密边界与撤回信号（关系阶段 ≠ 当前同意）
8. 自主冷却初始值

## 身份档（identity_profile）

先选择身份族，再选择或自拟具体身份（身份族见 `pools.yaml`「身份侧」；具体身份模板见 `scripts/data/identities.yaml`）。身份必须能解释角色拥有的资源、限制与社会风险。生成后只需补齐以下最小关系：

```yaml
identity_profile:
  role: null               # 校验器恢复锚点；与 public_identity 同义时复述
  public_identity: null    # 对外身份
  actual_function: null    # 实际职能；与公开身份一致则复述
  authority_source: null   # 权限/资源凭什么成立
  key_resource: null
  limitation: null
  obligation: null
  exposure_risk: null      # 暴露代价与社会风险
  hidden_mismatch: null    # 无隐藏身份则写 —
```

公开名声沿用 9a 已生成的字段，身份档只引用不重存。`hidden_mismatch` 可以为空——不要求每名角色都有隐藏身份。

三种容易混淆的身份，分辨方法是看人身关系和服务位置：「侍奉与身契」带依附或契约义务；「成人行业与感官服务」是可以自由进出的职业；「私密撮合与契约中介」只做牵线和保密安排，不亲自提供感官服务。

身份侧只回答一个问题：这个人凭什么能做什么。它替代不了处境压力、角色态度，更替代不了许可判定。

涉及反差时，先生成公开身份与私下场景的差异，再由独立亲密画像决定欲望与表现；`exposure_risk` 只表示暴露代价。

## 处境档（situation）

处境只决定角色正在承受的压力，不决定服从或许可（处境条目在 `pools.yaml`「处境侧」，每种处境的剧情模板在 `templates.yaml` 的 situation_beats）。正式结果只需补齐以下字段：

```yaml
situation:
  type: null
  trigger: null
  pressure: null
  immediate_objective: null
  deadline: null
  unresolved_choice: null
  knowledge_gap:
    player_knows: []      # 例：对方的真实身份
    npc_knows: []         # 例：门外还有第三方在等
    both_mistake: []      # 例：双方都以为对方已同意
  exits:
    available: true
    cost: null
    blocked_by: null
  consequence:
    immediate: null
    near_term: null
```

`type` 说明处境形态，`trigger` 说明刚刚发生的事，`pressure` 说明当前压力，`immediate_objective` 说明角色眼下想解决什么，`deadline` 和 `unresolved_choice` 共同制造行动窗口。`knowledge_gap` 只描述信息差，不替角色补写意志。

`exits` 必须明确暂停、离开或拒绝的可能；环境压力不自动变成许可。`consequence` 只写不处理的剧情后果。

> **错**：她被债务逼到墙角，所以今晚只能答应。
> **对**：她可以拒绝或离开，但要付代价——把代价写进退出通道里。

生成局势句：

```text
<角色> 因为 <触发事件>，正在 <地点/关系> 中面对 <当前压力>；
必须在 <期限> 前决定 <未完成选择>，否则 <可见后果> 将发生。
```

## 亲密画像（sexuality_profile）

开局只生成核心子集，进入亲密线后再按需展开。画像描述欲望与表达；许可判定只按 `SKILL.md`。

### 开局核心子集（主 NPC 必填）

```yaml
sexuality_profile:
  baseline: null           # 校验器恢复锚点；概括当前核心画像
  drive:
    intensity: low|medium|high
    awareness: unaware|uncertain|clear
  attraction:
    orientation: unspecified   # 该角色的吸引指向
    toward_player: null        # 对玩家是否具备吸引前提及原因
  preferences:
    initiative: follow|responsive|lead|switch
    pace: gradual|adaptive|direct
    style: tender|natural|playful|intense|experimental|mixed
  expression:
    directness: reserved|natural|direct|uninhibited
  regulation:
    self_control: stable|variable|poor
  interest_origin:
    type: stable|contextual|unexplored|defensive|target_specific
    reason: null   # 例：只对特定对象、源于某段经历、尚未探索
```

重要配角：开局可用同结构核心子集。普通功能配角：仅在剧情需要时生成精简画像。NPC 对玩家的性吸引必须由 `attraction` 的取向与具体原因独立支撑，不因玩家在场自动成立。

> **错**：两人独处、气氛到位，就默认她对他有意思。
> **对**：先在对玩家的吸引一栏写明具体前提和原因（比如「欣赏不戳穿她的人」），吸引才算成立。

### 按需展开（进入亲密线后）

需要更细写时再补，不要求开局填满：

```yaml
# 可选展开
background: {knowledge, experience, mistaken_beliefs}
preferences_extra: {emotional_link, exclusivity, novelty, turn_ons, turn_offs}
expression_extra: {teasing, verbal_expression, physical_initiative, public_mask, private_style}
regulation_extra: {inhibition, conflict_or_shame, compulsivity, aftermath_need}
```

高欲望或大胆表现不等于 `compulsivity`；只有持续失控并产生负面后果时才记录强迫风险。

### 变化状态

```yaml
sexuality_development:
  baseline: {}          # 开局核心快照
  current: {}           # 当前核心快照
  plasticity: low|medium|high   # 开局可只记总可塑性；展开后再分轴
  evidence: []
  trend: stable|opening|intensifying|conflicted|retreating
```

更新 `current` 须有至少两条跨回合且方向一致的事件证据；变化来自探索或自我承认，不得因压力、边界违反或画像变化自动扩大许可。不得整卡翻转；「沉沦」只作正文主观效果。

> **错**：一个晚上就把画像从克制整个翻成放开。
> **对**：攒够两条不同回合、方向一致的证据（比如先主动破了例，后来自己承认是期待的），才小幅更新当前状态。

## 表里双语态

适用范围：进入亲密线的角色（主 NPC、重要配角，以及任何实际参与亲密互动的配角），都要在 9f 语言滤镜里写出两档语态。

本节只管两档怎么写；什么时候切换、失控了怎么写，归 `SKILL.md`「语态调度」「失控语言退化」。

**书写格式**（程序按这个切分，必须遵守）：滤镜成段时，按「表层语态：……里层语态：……切换触发：……」的顺序写。`live_slice.py` 在「里层」第一次出现的位置切开，前半段当表层放进开局简介；缺了标记，整段（包括里层的话）都会被当成表层输出。

> **对**：「表层语态：句短、客气，回避正面回答。里层语态：直接，想要什么直说。切换触发：独处、酒意，或对方让她别装。」
> **错**：整段只写了表层一层；或者把里层写在前半段——程序一刀切下去就切错了位置。

- 表层语态：公开身份该有的说话方式。记句长、礼貌度、称呼、回避方式和压力下口吻。身份越端正，此档越不出现性器官粗词。
- 里层语态：卸下身份外壳后的说话方式。记直白程度、惯用荤词、主动或索求的措辞、失控时的口头习惯。
- 切换触发：写明该角色从表层切到里层通常需要什么，例如玩家明确要求、酒意、疼痛、快感累积、关系深化、独处或某个特定称呼。

两档落差由角色决定，不要求人人反差强烈：本就直白的角色两档接近，克制端正的角色落差大。双语态只描述说话方式，不改人格、目标、底线、亲密画像或当前许可。抽取了表层风味与口癖时，两档都应保留可辨认的同一人特征，不写成两个人。

## 角色决策卡

主 NPC 与重要配角保存决策卡；普通配角用精简值。运行时决策顺序以 `SKILL.md`「NPC 决策」为准。

```yaml
decision_card:
  goal: null               # 校验器恢复锚点；与 goals.primary 保持一致
  stable_core: {identity: null, core_traits: [], hard_limits: []}
  goals: {primary: null, secondary: null, hidden: null}
  knowledge: {known: [], unknown: [], mistaken_beliefs: []}
  pressure_response: {low: null, medium: null, high: null, critical: null}
  action_preferences: {prefer: [], avoid: [], never: []}
  sexuality_refs: {profile: sexuality_profile, development: sexuality_development}
```

决策卡不保存 `autonomy` 字段（NPC 顶层 `autonomy` 的完整结构是自主冷却的唯一正式来源，决策卡只读不存副本）。决策卡本身是开局校验产物，运行时只读 NPC 顶层的目标、底线、知识和 `autonomy`，不得另写可漂移的副本。

> **错**：把冷却截止回合抄一份存进决策卡。
> **对**：自主冷却只活在 NPC 顶层的 autonomy 里，决策卡最多引用它。

# 第四部分 角色类型与层级

## 角色层级与持久化

每个 NPC 保存 `role_level: main|important_supporting|supporting`，用于确定生成和存档深度。多数局只有一名主 NPC；后宫、群像或多主角局允许多名 `main`，每名都须完成完整主 NPC 全维角色卡与合格审计。

- `main`：保存完整核心字段，以及 `identity_profile`、`situation`、`decision_card`、`sexuality_profile`、`sexuality_development` 和 `naming_audit`。
- `important_supporting`：保存核心字段和决策卡；身份、处境与亲密画像按剧情相关性保存。
- `supporting`：字段清单以「配角」一节为准，那里是唯一版本；其余扩展字段可省略，五个表现字段（即 `core_personality`、`pressure_strategy`、`voice_filter`、`withdrawal_signal`、`emotion`）只在有值时保存，且保持文字形式（进入亲密线前的升级要求见下方升级规则）。

角色关系只以顶层 `relationships` 为正式来源。人物卡可在生成阶段计算初始关系，但落档后不得另存会与 `relationships` 冲突的 `relation` 数值。多名 `main` 之间的关系同样只以顶层 `relationships` 为正式来源，须在步骤 14 一并生成。

**普通配角升级**：普通配角实际进入亲密线前，须先即时补齐亲密核心子集、双语态、非空 `core_personality`、`pressure_strategy`、`voice_filter`、`withdrawal_signal`、`emotion`、决策卡与完整自主冷却，再将 `role_level` 提升为 `important_supporting`；保留原稳定 ID、姓名、近期记忆和顶层关系边，不得用升级重建角色或覆盖关系。（升级那一刻按本清单补齐；还没升级的重要配角，身份、处境与画像仍然按剧情相关性取舍。）

> **错**：升级时另起一张新卡、顺手把关系边重写。
> **对**：还是原来那个 ID、原来那个名字，把清单字段补齐后，把 role_level 改成 important_supporting。

## 配角

配角功能独立生成（盟友、阻力、见证者、信息源、竞争者、后果承接者、引路人、误导者、催化剂、庇护者、传话人、监视者等，清单在 `character_meta.yaml`）。

步骤 13 顺序：功能确认 → 配角简起名 → 核心价值与压力策略 → 其余字段。每名配角保存：姓名、年龄≥18、身份、功能（写入可选扩展字段 `function`）、与玩家/主 NPC 关系（落档于顶层 `relationships`）、目标、底线、已知信息、当前位置、一个标志细节。重要配角保存亲密核心子集；普通配角仅在剧情相关时生成精简画像。缺合格简审计则步骤 13 未完成。

## 玩家化身

生成前处理姓名：开局默认玩家为男性角色（主 NPC 默认为女性角色），姓名严格按性别专属名池（男主 `given_male` / 女主 `given_female`）抽取；预锁则只合规与去重；未预锁则标准起名并写入 `naming_audit`。称谓、年龄段、社会位置优先采用结构骰 `玩家称谓` / `玩家年龄段` / `玩家社会位置`。抽中「学长」或成年人培训/师生意象时，须声明为成年人教育、职业培训或成年社群。然后生成：

```text
player_id｜姓名｜年龄≥18｜性别/称谓｜公开身份
外貌与身体基线
可用资源 1-3 项
已知信息起点
社会处境与风险
玩家硬边界列表
```

落档时 `player_naming_audit` 只保留 `chosen` / `source` / `approved_turn`（须与 `player.name` 一致）；`checks` 与候选名单开局用完后不必进存档。

性别/称谓写入可选扩展字段 `appellation`（有值才保存，缺失按姓名与身份自然称呼）；玩家硬边界初始可为空，经「本局不碰 X」命令维护。不得替玩家补写长期目标、内心同意或不可撤回决定。
